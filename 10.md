## 0. Préparer le lab

Deux petites modifications du `~/lab/Dockerfile` : installer `rsync`, et demander au serveur SSH d'écrire ses logs sur la sortie d'erreur (`-e`), pour pouvoir les lire avec `docker compose logs`. Ajoutez une ligne `RUN` et modifiez la ligne `CMD`, **à la fin du fichier** :

```dockerfile
# ... (début du Dockerfile inchangé)

RUN apt-get update && apt-get install -y rsync && rm -rf /var/lib/apt/lists/*

```

Placer les ajouts à la fin permet à Docker de réutiliser le cache des couches précédentes : la reconstruction ne prend que quelques secondes.

```bash
cd ~/lab
docker compose up -d --build
docker compose logs -f bastion     # les logs de sshd (Ctrl+C pour quitter)
```

Côté WSL, vérifiez que vous avez les outils nécessaires :

```bash
sudo apt install -y openssh-client rsync
```

## 1. Qu'est-ce que SSH ?

**SSH** (*Secure Shell*) permet d'ouvrir une session sur une machine distante à travers un **canal chiffré**. Au-delà du simple terminal à distance, il sert à exécuter des commandes, transférer des fichiers, faire passer d'autres connexions dans des tunnels chiffrés, et il est le transport utilisé par Git, Ansible, rsync et de nombreux outils de déploiement.

Il repose sur deux programmes :

- le **client** `ssh`, sur votre machine ;
- le **serveur** `sshd` (*SSH daemon*), sur la machine distante, qui écoute par défaut sur le **port 22**.

Une connexion SSH se déroule en trois temps :

1. **Le serveur prouve son identité** au client avec sa **clé d'hôte**. Le client vérifie qu'il parle bien à la bonne machine.
2. **Un canal chiffré** est négocié entre les deux.
3. **L'utilisateur prouve son identité** au serveur, par mot de passe ou, mieux, par clé.

```bash
ssh student@serveur              # utilisateur@machine
ssh -p 2222 student@localhost    # sur un port différent
ssh serveur                      # utilise votre nom d'utilisateur local
```

## 2. La vérification de l'hôte

### La première connexion

```
$ ssh -p 2222 student@localhost
The authenticity of host '[localhost]:2222 ([127.0.0.1]:2222)' can't be established.
ED25519 key fingerprint is SHA256:Xk7c1V2aM...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Le client ne connaît pas encore ce serveur. Il affiche l'**empreinte** (*fingerprint*) de sa clé d'hôte et demande si vous lui faites confiance. En répondant `yes`, l'empreinte est enregistrée dans `~/.ssh/known_hosts`. Aux connexions suivantes, le client vérifie que le serveur présente toujours la même clé.

C'est le modèle de la **confiance à la première utilisation** (*TOFU*, *Trust On First Use*). En toute rigueur, il faudrait comparer cette empreinte avec celle communiquée par l'administrateur du serveur, qu'on obtient sur le serveur avec :

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

### Quand la clé change

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
```

Le serveur présente une clé différente de celle enregistrée, et SSH refuse de se connecter. Deux explications possibles :

- **une raison légitime** : le serveur a été réinstallé, recréé (c'est le cas de nos conteneurs à chaque reconstruction du lab), ou sa clé a été régénérée ;
- **une attaque** : quelqu'un s'est placé entre vous et le serveur (*man-in-the-middle*) et se fait passer pour lui.

> ⚠️ Ne supprimez jamais l'avertissement par réflexe. Vérifiez d'abord que le changement est attendu. Sur un serveur de production qu'on n'a pas touché, cet avertissement doit être pris très au sérieux.

Une fois le changement confirmé comme légitime, on supprime l'ancienne empreinte :

```bash
ssh-keygen -R "[localhost]:2222"     # pour un port non standard, la syntaxe est [hôte]:port
ssh-keygen -R web
```

## 3. Exécuter des commandes à distance

Tout ce qui suit l'adresse est exécuté sur la machine distante, puis la connexion se ferme :

```bash
ssh -p 2222 student@localhost uptime
ssh -p 2222 student@localhost 'df -h / && free -h'
ssh -p 2222 student@localhost 'sudo tail -n 20 /var/log/dpkg.log'
```

La sortie de la commande distante revient sur votre machine, et peut donc être traitée localement :

```bash
ssh serveur 'cat /var/log/nginx/access.log' | awk '{print $1}' | sort | uniq -c | sort -rn | head
ssh serveur 'tar czf - /etc' > etc-serveur.tar.gz           # une sauvegarde qui transite par SSH
```

Pour une commande interactive (un éditeur, `top`, `sudo` qui demande un mot de passe), il faut forcer l'allocation d'un terminal avec `-t` :

```bash
ssh -t serveur htop
ssh -t serveur 'sudo nano /etc/hosts'
```

> 💡 Attention aux guillemets. Avec des apostrophes, les variables sont interprétées **sur le serveur** ; avec des guillemets doubles, elles sont remplacées **localement** avant l'envoi : `ssh serveur 'echo $HOSTNAME'` et `ssh serveur "echo $HOSTNAME"` n'affichent pas la même chose.

### Les séquences d'échappement

Une session SSH qui ne répond plus (réseau coupé, machine en veille) peut bloquer le terminal pendant de longues minutes. Le client SSH reconnaît des séquences spéciales, tapées **en début de ligne** :

| Séquence | Effet |
|---|---|
| `Entrée` puis `~.` | Couper immédiatement la connexion |
| `Entrée` puis `~?` | Liste des séquences disponibles |

## 4. L'authentification par clé

### Le principe

L'authentification par mot de passe a de nombreux défauts : les mots de passe se devinent, se réutilisent, et peuvent être attaqués par force brute par n'importe qui sur Internet. L'authentification par **clé** repose sur une paire de clés :

- la **clé privée** reste sur votre machine, et ne doit **jamais** la quitter ni être partagée ;
- la **clé publique** peut être distribuée librement : on la dépose sur chaque serveur auquel on veut accéder.

À la connexion, le serveur envoie un défi que seul le détenteur de la clé privée peut signer. Le serveur vérifie la signature avec la clé publique. La clé privée ne circule jamais sur le réseau.

### Générer une paire de clés

```bash
ssh-keygen -t ed25519 -C "prenom.nom@entreprise"
```

```
Enter file in which to save the key (/home/student/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
```

`ed25519` est l'algorithme recommandé : moderne, rapide, et ses clés sont courtes. Le commentaire `-C` sert à identifier la clé, par exemple dans les fichiers des serveurs. Deux fichiers sont créés :

```
~/.ssh/id_ed25519        ← clé privée (permissions 600)
~/.ssh/id_ed25519.pub    ← clé publique
```

> 🔒 **Protégez votre clé privée par une phrase de passe.** Sans elle, quiconque récupère le fichier (vol de portable, sauvegarde mal protégée, malware) accède à tous vos serveurs. Avec un agent SSH (section 5), la phrase de passe n'est demandée qu'une fois par session : ce n'est pas une contrainte au quotidien.

> 💡 Sur d'anciens systèmes qui ne connaissent pas ed25519, on utilise `ssh-keygen -t rsa -b 4096`. Les clés DSA et les clés RSA de moins de 2048 bits sont à proscrire.

### Déposer la clé publique sur un serveur

Côté serveur, les clés publiques autorisées pour un utilisateur sont listées dans `~/.ssh/authorized_keys`, une par ligne. La façon la plus simple de l'y ajouter :

```bash
ssh-copy-id -p 2222 student@localhost
```

`ssh-copy-id` se connecte (une dernière fois par mot de passe), crée le dossier `~/.ssh` du serveur avec les bonnes permissions, et ajoute la clé à `authorized_keys`. À la main, cela revient à :

```bash
cat ~/.ssh/id_ed25519.pub | ssh -p 2222 student@localhost \
  'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
```

### Les permissions, encore

SSH est très strict sur les permissions, et refuse d'utiliser des fichiers trop ouverts (chapitre 4) :

| Fichier | Permissions |
|---|---|
| `~/.ssh/` | `700` |
| `~/.ssh/id_ed25519` (clé privée) | `600` |
| `~/.ssh/id_ed25519.pub` | `644` |
| `~/.ssh/authorized_keys` | `600` |
| `~/.ssh/config` | `600` |
| Le dossier personnel lui-même | Pas d'écriture pour le groupe ni les autres |

Côté client, une clé privée trop ouverte provoque l'erreur `UNPROTECTED PRIVATE KEY FILE!`. Côté serveur, un `authorized_keys` ou un home trop permissif fait **silencieusement** ignorer la clé : le serveur demande alors un mot de passe, sans explication. Les logs du serveur, eux, donnent la raison.

### Restreindre une clé

Une ligne de `authorized_keys` peut être précédée d'options qui limitent ce que la clé permet de faire :

```
from="10.0.0.0/8",no-port-forwarding,no-agent-forwarding ssh-ed25519 AAAA... ci@entreprise
command="/opt/scripts/backup.sh",restrict ssh-ed25519 AAAA... backup@serveur
```

La première clé n'est acceptée que depuis le réseau interne. La seconde ne peut exécuter qu'une seule commande, quoi que demande le client : idéal pour une clé utilisée par un processus automatique.

## 5. L'agent SSH

Si votre clé est protégée par une phrase de passe, il faut la taper à chaque connexion. L'**agent SSH** garde les clés déverrouillées en mémoire pendant la session :

```bash
eval "$(ssh-agent -s)"           # démarrer un agent (s'il n'y en a pas déjà un)
ssh-add                          # ajouter la clé par défaut (demande la phrase de passe une fois)
ssh-add ~/.ssh/autre_cle         # ajouter une autre clé
ssh-add -l                       # lister les clés chargées
ssh-add -D                       # vider l'agent
ssh-add -t 4h                    # ajouter la clé pour 4 heures seulement
```

Sur un poste de travail Linux, un agent est généralement lancé automatiquement avec la session graphique. Dans WSL, il faut le démarrer soi-même ; on peut ajouter ces lignes à `~/.bashrc` :

```bash
if [ -z "$SSH_AUTH_SOCK" ]; then
  eval "$(ssh-agent -s)" > /dev/null
fi
```

### Le transfert d'agent : à éviter

L'option `-A` (*agent forwarding*) permet d'utiliser votre agent depuis le serveur distant, par exemple pour rebondir vers une autre machine ou faire un `git pull` avec vos clés.

> 🔒 **Le transfert d'agent est risqué.** Pendant toute la durée de votre connexion, root sur le serveur intermédiaire (ou quiconque l'a compromis) peut utiliser votre agent pour se connecter **partout où vos clés donnent accès**. Pour rebondir sur un bastion, utilisez `ProxyJump` (section 7), qui ne présente pas ce risque.

## 6. Le fichier `~/.ssh/config`

Taper `ssh -p 2222 -i ~/.ssh/id_ed25519 student@localhost` à chaque fois devient vite pénible. Le fichier `~/.ssh/config` permet de définir des **alias** avec tous leurs paramètres :

```
Host bastion
    HostName localhost
    Port 2222
    User student
    IdentityFile ~/.ssh/id_ed25519

Host prod-api
    HostName 203.0.113.42
    User deploy
    IdentityFile ~/.ssh/id_prod
```

```bash
ssh bastion              # au lieu de : ssh -p 2222 -i ~/.ssh/id_ed25519 student@localhost
scp fichier.txt bastion:/tmp/
```

Ces alias fonctionnent avec **tous** les outils qui utilisent SSH : `scp`, `rsync`, `git`, Ansible, l'extension Remote-SSH de VS Code...

Les directives les plus utiles :

| Directive | Rôle |
|---|---|
| `HostName` | L'adresse réelle (nom ou IP) |
| `User` | L'utilisateur distant |
| `Port` | Le port |
| `IdentityFile` | La clé à utiliser |
| `IdentitiesOnly yes` | N'essayer **que** la clé indiquée, pas toutes celles de l'agent |
| `ProxyJump` | Rebondir par une autre machine (section 7) |
| `LocalForward` | Créer un tunnel à chaque connexion (section 9) |
| `ServerAliveInterval 60` | Envoyer un signe de vie toutes les 60 secondes, pour éviter les coupures dues à l'inactivité |
| `ForwardAgent no` | Ne pas transférer l'agent (valeur par défaut, à laisser ainsi) |

### Motifs et ordre de lecture

`Host` accepte plusieurs noms et des jokers. Pour chaque paramètre, **la première valeur trouvée l'emporte** : on place donc les règles spécifiques en haut et les règles générales à la fin.

```
Host web db
    User student
    ProxyJump bastion

Host *.prod.entreprise.com
    User deploy
    IdentityFile ~/.ssh/id_prod

Host *
    ServerAliveInterval 60
    IdentitiesOnly yes
```

> 💡 `IdentitiesOnly yes` évite l'erreur `Too many authentication failures` : quand l'agent contient beaucoup de clés, le client les essaie toutes, et le serveur coupe la connexion après quelques échecs, avant même d'arriver à la bonne.

## 7. Rebondir par un bastion : `ProxyJump`

Dans une infrastructure bien conçue, les serveurs ne sont pas directement accessibles depuis Internet. On passe par une machine unique, exposée et très surveillée : le **bastion** (*jump host*). C'est exactement la situation du lab : depuis WSL, seul `bastion` est joignable, et `web` et `db` ne le sont que depuis `bastion`.

```bash
ssh -J bastion student@web              # rebondir par bastion pour atteindre web
ssh -J bastion,web student@db           # plusieurs rebonds successifs
```

Avec `ProxyJump`, votre client ouvre une connexion vers le bastion, puis demande au bastion de relayer une **seconde connexion SSH, chiffrée de bout en bout**, vers la machine cible. Le bastion ne voit passer que du trafic chiffré, et vos clés restent sur votre machine : il n'y a rien à copier sur le bastion, et pas besoin de transférer l'agent.

```
WSL ──── SSH ────► bastion ──── relais TCP ────► web
 └────────────── SSH de bout en bout ───────────┘
```

Dans `~/.ssh/config` :

```
Host web db
    User student
    ProxyJump bastion
```

```bash
ssh web          # passe automatiquement par bastion
ssh db
```

Le nom `web` est résolu **par le bastion** : c'est lui qui ouvre la connexion vers la cible. Il suffit donc que le bastion sache joindre `web`.

## 8. Transférer des fichiers

### `scp`

```bash
scp fichier.txt bastion:/tmp/                 # envoyer
scp bastion:/etc/hostname ./                  # récupérer
scp -r dossier/ web:~/                        # un dossier
scp -P 2222 fichier.txt student@localhost:~/  # port : -P majuscule (contrairement à ssh)
```

`scp` est simple et disponible partout, mais il recopie tout à chaque fois.

### `rsync`

`rsync` synchronise des fichiers et ne transfère que **les différences**. C'est l'outil de référence pour les déploiements simples, les sauvegardes et les copies volumineuses.

```bash
rsync -avz projet/ web:~/projet/              # synchroniser
rsync -avzn projet/ web:~/projet/             # -n : simulation, affiche ce qui serait fait
rsync -avz --delete projet/ web:~/projet/     # supprimer aussi les fichiers disparus de la source
rsync -avz --exclude '.git' --exclude 'node_modules' projet/ web:~/projet/
rsync -avz --progress gros-fichier.iso web:~/  # afficher la progression
rsync -avz -e 'ssh -p 2222' projet/ student@localhost:~/projet/   # options SSH explicites
```

| Option | Rôle |
|---|---|
| `-a` | Mode archive : récursif, et préserve permissions, dates, liens symboliques |
| `-v` | Affiche les fichiers transférés |
| `-z` | Compresse pendant le transfert |
| `-n` | Simulation (*dry run*) |
| `--delete` | Supprime dans la destination ce qui n'existe plus dans la source |
| `--exclude` | Ignore des fichiers |

> ⚠️ **La barre oblique finale de la source change tout.** `rsync -a projet/ dest/` copie le **contenu** de `projet` dans `dest`. `rsync -a projet dest/` copie le **dossier** `projet` lui-même, qui devient `dest/projet`. Combinée à `--delete`, une erreur de barre oblique peut effacer une arborescence entière : lancez toujours d'abord avec `-n`.

`rsync` doit être installé sur les **deux** machines.

### `sftp`

`sftp` ouvre une session interactive de transfert de fichiers, comme un client FTP, mais au-dessus de SSH. C'est aussi ce qu'utilisent les clients graphiques comme FileZilla ou WinSCP.

```bash
sftp bastion
sftp> ls
sftp> put fichier.txt
sftp> get /etc/hostname
sftp> exit
```

## 9. Les tunnels

SSH peut faire passer n'importe quelle connexion TCP dans son canal chiffré. C'est l'une de ses fonctionnalités les plus puissantes, et les plus utiles pour un développeur.

### Le tunnel local : `-L`

Accéder depuis votre machine à un service qui n'est joignable que depuis le serveur :

```bash
ssh -L 15432:db:5432 bastion
```

Se lit : « ouvre le port **15432** sur ma machine ; tout ce qui s'y connecte est transporté par SSH jusqu'à `bastion`, qui le transmet à **`db:5432`** ». Vous pouvez alors vous connecter à la base de données avec votre client habituel, sur `localhost:15432`, alors qu'elle n'est pas exposée.

```
Votre poste :15432 ══ SSH ══► bastion ──► db:5432
```

La destination est résolue **par le serveur SSH** : `db` doit être joignable depuis `bastion`. La destination peut aussi être `localhost`, du point de vue du serveur : `ssh -L 18000:localhost:8000 web` donne accès à un service qui n'écoute que sur la boucle locale de `web`. C'est la bonne façon d'administrer un outil qui ne doit pas être exposé.

### Le tunnel inverse : `-R`

L'inverse : rendre un service de **votre** machine accessible depuis le serveur.

```bash
ssh -R 9000:localhost:3000 web
```

Se lit : « ouvre le port **9000** sur `web` ; tout ce qui s'y connecte est transporté jusqu'à ma machine, vers **`localhost:3000`** ». Utile pour montrer une application en cours de développement depuis un serveur, ou pour recevoir un webhook. Par défaut, le port n'est ouvert que sur la boucle locale du serveur (option `GatewayPorts` de `sshd` pour changer ce comportement).

### Le proxy dynamique : `-D`

`-D` transforme la connexion SSH en **proxy SOCKS** : toutes les applications configurées pour l'utiliser passent par le serveur, vers n'importe quelle destination.

```bash
ssh -D 1080 bastion
curl --socks5-hostname localhost:1080 http://web/
```

Pratique pour naviguer sur les interfaces web d'un réseau interne depuis son navigateur.

### Options utiles pour les tunnels

```bash
ssh -N -L 15432:db:5432 bastion        # -N : pas de shell, seulement le tunnel
ssh -f -N -L 15432:db:5432 bastion     # -f : passer en arrière-plan
```

Et dans `~/.ssh/config`, pour que le tunnel s'ouvre à chaque connexion :

```
Host tunnel-db
    HostName localhost
    Port 2222
    User student
    LocalForward 15432 db:5432
```

> 🔒 Les tunnels contournent les pare-feu : c'est leur intérêt, et leur danger. Un tunnel inverse ouvert depuis un poste de l'entreprise vers un serveur extérieur crée une porte d'entrée dans le réseau interne. Sur un bastion, on peut interdire les tunnels avec `AllowTcpForwarding no`, ou les limiter avec `PermitOpen`.

## 10. Le serveur SSH

### La configuration

La configuration du serveur se trouve dans `/etc/ssh/sshd_config`. Sur Ubuntu, ce fichier commence par :

```
Include /etc/ssh/sshd_config.d/*.conf
```

Les fichiers de `/etc/ssh/sshd_config.d/` sont donc lus **avant** le reste du fichier, dans l'ordre alphabétique. Et comme pour le client, **la première valeur trouvée pour un paramètre l'emporte**. La bonne pratique est de placer ses réglages dans un fichier dédié, par exemple `/etc/ssh/sshd_config.d/10-durcissement.conf`, plutôt que de modifier le fichier principal.

> ⚠️ Conséquence surprenante de la règle « première valeur » : un paramètre défini dans un fichier de `sshd_config.d/` (par exemple par cloud-init dans `50-cloud-init.conf`) **l'emporte** sur ce que vous écrivez dans `sshd_config`. Si une modification semble sans effet, c'est souvent la raison. `sshd -T` affiche la configuration réellement appliquée.

### Les réglages de sécurité essentiels

```
# /etc/ssh/sshd_config.d/10-durcissement.conf

# Pas de connexion directe en root : on se connecte avec son compte, puis sudo
PermitRootLogin no

# Uniquement l'authentification par clé
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes

# Uniquement certains utilisateurs ou groupes
AllowGroups ssh-users

# Limiter les tentatives par connexion
MaxAuthTries 3

# Couper les sessions inactives (300 s × 2 sans réponse)
ClientAliveInterval 300
ClientAliveCountMax 2

# Pas de transfert d'agent ni de X11 si ce n'est pas nécessaire
AllowAgentForwarding no
X11Forwarding no
```

`PasswordAuthentication no` est de loin la mesure la plus efficace : elle rend inutiles les attaques par force brute qui visent en permanence tous les serveurs SSH exposés sur Internet.

> 💡 Changer le port SSH (par exemple 2222 au lieu de 22) réduit fortement le bruit dans les logs, car les robots visent surtout le port 22. Mais ce n'est pas une mesure de sécurité en soi : un scan des ports le retrouve en quelques secondes. L'authentification par clé, elle, en est une.

### Appliquer les modifications sans se couper l'accès

Une erreur dans la configuration de `sshd` peut vous interdire l'accès à un serveur distant, sans autre moyen d'y revenir que la console de l'hébergeur. La procédure à suivre **systématiquement** :

1. **Garder une session SSH ouverte** pendant toute l'opération. Les sessions existantes ne sont pas coupées par un rechargement.
2. **Tester la syntaxe** : `sudo sshd -t` (aucune sortie signifie aucune erreur).
3. **Vérifier la configuration effective** : `sudo sshd -T | grep -i passwordauthentication`.
4. **Recharger** le service : `sudo systemctl reload ssh` (sur Ubuntu, le service s'appelle `ssh` ; sur Red Hat, `sshd`).
5. **Tester depuis une nouvelle session**, sans fermer la première.
6. Seulement alors, fermer la session de secours.

> 💡 Sur Ubuntu 24.04, SSH est démarré par **activation de socket** (`ssh.socket`) : le port d'écoute est défini par cette unité systemd. Pour changer de port, il faut, en plus de modifier `Port`, lancer `sudo systemctl daemon-reload` puis `sudo systemctl restart ssh.socket`.

Dans les conteneurs du lab, `sshd` n'est pas géré par systemd : c'est le PID 1 du conteneur. On lui demande de relire sa configuration en lui envoyant `SIGHUP` (chapitre 5) : `kill -HUP 1`.

### Les logs

```bash
sudo journalctl -u ssh -f                  # sur un serveur Ubuntu avec systemd
sudo grep sshd /var/log/auth.log | tail    # selon la configuration
docker compose logs -f web                 # dans le lab
```

On y lit chaque connexion réussie ou refusée, avec l'utilisateur, l'adresse source et la méthode d'authentification :

```
Accepted publickey for student from 172.19.0.2 port 51234 ssh2: ED25519 SHA256:Xk7...
Failed password for invalid user admin from 198.51.100.7 port 40022 ssh2
Authentication refused: bad ownership or modes for directory /home/student/.ssh
```

> 💡 Sur un serveur exposé à Internet, les logs se remplissent de tentatives de connexion automatisées. L'outil **fail2ban** surveille ces logs et bloque temporairement dans le pare-feu les adresses qui accumulent les échecs.

## 11. Diagnostiquer une connexion SSH

L'option `-v` (jusqu'à `-vvv`) affiche le déroulement détaillé de la connexion côté client : fichiers de configuration lus, clés essayées, méthodes acceptées par le serveur.

```bash
ssh -v web
```

```
debug1: Reading configuration data /home/student/.ssh/config
debug1: Connecting to localhost [127.0.0.1] port 2222.
debug1: Offering public key: /home/student/.ssh/id_ed25519 ED25519 SHA256:...
debug1: Authentications that can continue: publickey,password
```

| Erreur | Cause probable |
|---|---|
| `Connection refused` | Rien n'écoute sur ce port : `sshd` arrêté, mauvais port (chapitre 9) |
| `Connection timed out` | Machine injoignable ou pare-feu |
| `Host key verification failed` | La clé d'hôte a changé (section 2) |
| `Permission denied (publickey)` | Aucune clé acceptée, et les mots de passe sont désactivés. Mauvaise clé, mauvais utilisateur, clé absente de `authorized_keys`, ou permissions incorrectes côté serveur |
| `Permission denied (publickey,password)` | Idem, et le mot de passe a été refusé |
| `UNPROTECTED PRIVATE KEY FILE!` | Clé privée trop ouverte : `chmod 600` |
| `Too many authentication failures` | Trop de clés essayées : `IdentitiesOnly yes` et `IdentityFile` |

Pour une erreur d'authentification, les messages du client restent volontairement vagues (pour ne pas renseigner un attaquant) : la vraie raison est dans les **logs du serveur**.

## 12. SSH au quotidien du développeur

### Git

Les plateformes Git (GitHub, GitLab, Bitbucket) acceptent l'authentification par clé SSH. On y dépose sa clé publique dans les paramètres du compte, puis :

```bash
ssh -T git@github.com
# Hi prenom! You've successfully authenticated, but GitHub does not provide shell access.
git clone git@github.com:organisation/projet.git
```

### Réutiliser les connexions

Chaque connexion SSH demande une négociation qui prend un peu de temps, surtout à travers un bastion. Le **multiplexage** réutilise une connexion existante pour les suivantes :

```
Host *
    ControlMaster auto
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
```

La première connexion ouvre un canal maître, que les suivantes (y compris `scp`, `rsync`, `git`) réutilisent instantanément pendant 10 minutes.

### Windows et WSL

Windows dispose de son propre client OpenSSH (dans PowerShell), avec ses propres clés dans `C:\Users\<nom>\.ssh\`. Les clés et la configuration de WSL (`~/.ssh/` dans Ubuntu) sont **distinctes**. Si vous utilisez des outils Windows (VS Code, un client Git Windows) et des outils WSL, gardez en tête qu'ils ne partagent pas les mêmes clés par défaut.

### Exercice 10.5 — Tunnels (niveau intermédiaire)

1. Sur `db`, lancez un petit serveur web **qui n'écoute que sur sa boucle locale** :

   Vérifiez qu'il est inaccessible depuis `web` et depuis le bastion.

4. Dans WSL, lancez un serveur web local sur le port 9000 (`python3 -m http.server 9000`, dans un dossier contenant un fichier de votre choix). Créez un tunnel inverse pour que `web` puisse y accéder sur son propre port 9000. Testez depuis `web`.
5. Bonus : créez un proxy SOCKS via le bastion, et utilisez-le avec `curl` pour atteindre `http://db:8001/hostname` par son nom.

<details>
<summary>Solution</summary>

```bash

ssh -N -L 18000:localhost:8000 db &                   # « localhost » vu depuis db
curl -s http://localhost:18000/hostname               # db
kill %1

docker compose -f ~/lab/docker-compose.yml exec -d db \
  bash -c 'cd /srv/interne && python3 -m http.server 8001 --bind 0.0.0.0'
ssh -N -L 18001:db:8001 bastion &                     # db est résolu et joint par le bastion
curl -s http://localhost:18001/hostname
kill %1

mkdir -p ~/partage && echo "Bonjour depuis WSL" > ~/partage/message.txt
```

Avec `--socks5-hostname`, c'est le proxy (donc le bastion) qui résout le nom `db`. Avec `--socks5` simple, `curl` essaierait de résoudre `db` localement, et échouerait.

### Exercice 10.6 — Durcir le serveur SSH (niveau intermédiaire)

Sur `web` (ouvrez un shell root avec `docker compose exec web bash`, qui vous servira de **session de secours**) :

2. Créez un fichier `/etc/ssh/sshd_config.d/10-durcissement.conf` qui interdit la connexion root et l'authentification par mot de passe, limite les tentatives à 3, et n'autorise que les membres d'un groupe `ssh-users`. Créez ce groupe et ajoutez-y `student`.
3. Testez la syntaxe, vérifiez la configuration effective, puis rechargez `sshd`.
4. Depuis WSL, vérifiez que la connexion par clé fonctionne toujours, et que la connexion par mot de passe est refusée. Lisez les logs du serveur.
5. Créez un utilisateur `intrus` avec un mot de passe et une copie de votre clé publique, **sans** l'ajouter au groupe `ssh-users`. Peut-il se connecter ?

<details>
<summary>Solution</summary>

```bash

sshd -T | grep -E -i "^(passwordauthentication|permitrootlogin|maxauthtries)"

groupadd ssh-users
usermod -aG ssh-users student

cat > /etc/ssh/sshd_config.d/10-durcissement.conf << 'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowGroups ssh-users

sshd -t && echo "Syntaxe OK"
sshd -T | grep -E -i "^(passwordauthentication|permitrootlogin|maxauthtries|allowgroups)"
kill -HUP 1
```

```bash
# WSL

ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password web   # Permission denied (publickey)
docker compose -f ~/lab/docker-compose.yml logs --tail 20 web
```

```bash
# shell root sur web
```

Si la configuration est invalide, `sshd` peut refuser de redémarrer au `SIGHUP` : comme il est le PID 1 du conteneur, celui-ci s'arrête.
