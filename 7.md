# Chapitre 7 — Gestion des paquets

## 1. Pourquoi des paquets ?

Sous Windows, on installe souvent un logiciel en téléchargeant un installeur depuis le site de l'éditeur. Sous Linux, la méthode normale est différente : on demande au **gestionnaire de paquets** d'installer le logiciel depuis les **dépôts** de la distribution.

Un **paquet** est une archive qui contient un logiciel (ses binaires, bibliothèques, fichiers de configuration par défaut, documentation) et des **métadonnées** : son nom, sa version, sa description, et surtout la liste de ses **dépendances**, c'est-à-dire les autres paquets dont il a besoin pour fonctionner.

Un **dépôt** est un serveur qui héberge des milliers de paquets, un index qui les décrit, et une signature cryptographique qui garantit leur authenticité.

Cette approche apporte beaucoup :

- **les dépendances sont résolues automatiquement** : installer `nginx` installe aussi les bibliothèques dont il a besoin ;
- **les mises à jour sont centralisées** : une seule commande met à jour tout le système, y compris les correctifs de sécurité ;
- **l'authenticité est vérifiée** : chaque paquet est signé, un paquet modifié en route est refusé ;
- **la désinstallation est propre** : le gestionnaire sait exactement quels fichiers appartiennent à quel paquet ;
- **le système est inventoriable** : on sait à tout moment ce qui est installé, et en quelle version.

> 💡 C'est pour cette raison qu'on évite, autant que possible, d'installer des logiciels « à la main » sur un serveur. Un binaire copié dans `/usr/bin` ne sera jamais mis à jour, et personne ne saura plus tard d'où il vient.

## 2. Les deux niveaux d'outils

Chaque famille de distributions a deux niveaux d'outils :

| | Famille Debian / Ubuntu | Famille Red Hat | Alpine |
|---|---|---|---|
| Format des paquets | `.deb` | `.rpm` | `.apk` |
| Outil bas niveau : installe un fichier paquet, sans gérer les dépendances ni les dépôts | `dpkg` | `rpm` | — |
| Outil haut niveau : dépôts, dépendances, mises à jour | `apt` (et `apt-get`) | `dnf` (ex-`yum`) | `apk` |

Au quotidien, on utilise l'outil haut niveau. L'outil bas niveau sert surtout à **interroger** la base des paquets installés.

## 3. `apt` au quotidien

### Mettre à jour l'index, puis le système

C'est la distinction la plus importante du chapitre, et une source de confusion permanente :

```bash
sudo apt update        # télécharge la liste à jour des paquets disponibles (n'installe RIEN)
sudo apt upgrade       # installe les nouvelles versions des paquets déjà installés
```

`apt update` rafraîchit le **catalogue** local : quelles versions existent dans les dépôts. `apt upgrade` utilise ce catalogue pour mettre à jour les paquets. Sans `update` préalable, `upgrade` travaille avec un catalogue périmé et peut ne rien trouver, et `install` peut échouer avec une erreur 404 sur un paquet qui n'existe plus dans cette version.

```bash
apt list --upgradable              # ce qui peut être mis à jour
sudo apt full-upgrade              # upgrade qui accepte aussi d'ajouter ou supprimer des paquets
```

`upgrade` ne supprime jamais un paquet installé. Quand une mise à jour nécessite de remplacer une dépendance, il la met de côté ; `full-upgrade` l'autorise. Sur un serveur, on lit ce que `full-upgrade` propose avant de valider.

### Installer et supprimer

```bash
sudo apt install htop jq tree      # installer un ou plusieurs paquets
sudo apt install -y curl           # sans demander confirmation
sudo apt install ./paquet.deb      # installer un .deb local, avec ses dépendances
sudo apt reinstall nginx           # réinstaller

sudo apt remove nginx              # supprimer le paquet, garder sa configuration
sudo apt purge nginx               # supprimer le paquet ET sa configuration
sudo apt autoremove                # supprimer les dépendances devenues inutiles
```

La différence entre `remove` et `purge` compte : après un `remove`, les fichiers de configuration modifiés dans `/etc` restent en place. Si vous réinstallez le paquet, vous retrouvez votre configuration. Si vous voulez vraiment repartir de zéro, c'est `purge`.

### Chercher et se renseigner

```bash
apt search "json processor"        # chercher dans les noms et descriptions
apt show jq                        # description, version, dépendances, taille
apt list --installed               # tous les paquets installés
apt list --installed | grep python # filtrer
apt-cache depends nginx            # dépendances d'un paquet
apt-cache rdepends libssl3         # quels paquets dépendent de celui-ci
```

### Dépendances et recommandations

Un paquet déclare plusieurs types de relations. Les **Depends** sont obligatoires. Les **Recommends** sont des paquets utiles mais non indispensables, qu'`apt` installe par défaut. Les **Suggests** ne sont jamais installés automatiquement.

```bash
sudo apt install --no-install-recommends nginx     # uniquement le strict nécessaire
```

C'est une option précieuse pour les serveurs et les images Docker : elle réduit la taille et la surface d'attaque.

### `apt` ou `apt-get` ?

`apt` est la commande moderne, pensée pour un usage interactif : barre de progression, couleurs, sortie lisible. `apt-get` et `apt-cache` sont les commandes historiques, dont le format de sortie est **stable** dans le temps. Dans un script ou un Dockerfile, on utilise `apt-get` ; `apt` affiche d'ailleurs un avertissement quand on l'utilise dans un pipe.

```bash
# Dans un script : non interactif, et sans questions de configuration
export DEBIAN_FRONTEND=noninteractive
apt-get update
apt-get install -y --no-install-recommends curl ca-certificates
```

## 4. `dpkg` : interroger le système

`dpkg` connaît tous les paquets installés et la liste exacte de leurs fichiers.

```bash
dpkg -l                            # liste des paquets installés
dpkg -l | grep nginx
dpkg -s curl                       # état et informations d'un paquet installé
dpkg -L curl                       # tous les fichiers installés par le paquet
dpkg -S /usr/bin/curl              # quel paquet a installé ce fichier ?
sudo dpkg -i paquet.deb            # installer un .deb (sans résoudre les dépendances)
```

Les deux premières lettres de `dpkg -l` indiquent l'état : `ii` signifie installé normalement, `rc` signifie supprimé mais avec sa configuration encore présente (après un `remove` sans `purge`).

> ⚠️ Sur Ubuntu récent, `/bin` est un lien vers `/usr/bin`, et `dpkg` ne connaît souvent que l'un des deux chemins : `dpkg -S /bin/ls` peut échouer alors que `dpkg -S /usr/bin/ls` répond `coreutils`. En cas de doute, passez le chemin réel : `dpkg -S "$(readlink -f "$(command -v ls)")"`.

### Trouver le paquet d'un fichier qui n'est pas installé

`dpkg -S` ne fonctionne que pour les paquets installés. Pour savoir quel paquet **fournirait** une commande ou un fichier :

```bash
sudo apt install apt-file
sudo apt-file update
apt-file search bin/dig            # → bind9-dnsutils: /usr/bin/dig
```

Sur Ubuntu, taper une commande absente déclenche aussi une suggestion automatique :

```
$ dig
Command 'dig' not found, but can be installed with:
sudo apt install bind9-dnsutils
```

## 5. Les dépôts

### Où sont-ils définis ?

Les dépôts sont déclarés dans `/etc/apt/sources.list` et dans les fichiers de `/etc/apt/sources.list.d/`. Depuis Ubuntu 24.04, les dépôts officiels sont décrits dans `/etc/apt/sources.list.d/ubuntu.sources`, au format dit *deb822* :

```
Types: deb
URIs: http://archive.ubuntu.com/ubuntu/
Suites: noble noble-updates noble-backports
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

On retrouve encore partout l'ancien format sur une ligne, qui est équivalent :

```
deb [signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg] http://archive.ubuntu.com/ubuntu noble main universe
```

| Élément | Signification |
|---|---|
| `noble` | Nom de code de la version d'Ubuntu (24.04). `lsb_release -cs` ou `/etc/os-release` le donnent |
| `noble-updates` | Mises à jour correctives publiées après la sortie |
| `noble-security` | Correctifs de sécurité |
| `main` | Logiciels libres maintenus officiellement par Canonical |
| `universe` | Logiciels libres maintenus par la communauté |
| `restricted`, `multiverse` | Pilotes propriétaires, logiciels non libres |

### Les versions LTS

Ubuntu publie une version tous les six mois, et une version **LTS** (*Long Term Support*) tous les deux ans, en avril des années paires : 22.04, 24.04, 26.04... Les LTS reçoivent des mises à jour de sécurité pendant au moins cinq ans. Sur un serveur, on utilise une LTS.

Conséquence importante : **les versions des logiciels sont figées** pendant toute la vie d'une version d'Ubuntu. Seuls les correctifs de sécurité et de bugs sont appliqués. C'est ce qui garantit la stabilité, mais c'est aussi pourquoi le `nodejs` ou le `postgresql` des dépôts officiels est souvent plus ancien que la dernière version publiée.

### Ajouter un dépôt tiers

Pour obtenir une version plus récente d'un logiciel, ou un logiciel absent des dépôts officiels, on ajoute le dépôt de son éditeur. La procédure suit toujours le même schéma : récupérer la **clé de signature** du dépôt, la placer dans `/etc/apt/keyrings/`, déclarer le dépôt en indiquant cette clé avec `signed-by`, puis mettre à jour l'index.

Exemple avec le dépôt officiel de GitHub CLI :

```bash
sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg \
  | sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
  | sudo tee /etc/apt/sources.list.d/github-cli.list
sudo apt update
sudo apt install gh
```

L'option `signed-by` limite la confiance accordée à cette clé : elle ne sert qu'à vérifier **ce** dépôt. L'ancienne commande `apt-key add`, qui ajoutait une clé valable pour tous les dépôts, est obsolète et ne doit plus être utilisée, même si on la trouve encore dans de nombreux tutoriels.

> 🔒 **Ajouter un dépôt, c'est donner à son éditeur le droit d'installer du code en root sur votre machine** à chaque mise à jour. Ne le faites que pour des éditeurs de confiance, et suivez leur documentation officielle.

### Les PPA

Sur Ubuntu, les **PPA** (*Personal Package Archives*) sont des dépôts hébergés sur Launchpad, souvent maintenus par des particuliers. `sudo add-apt-repository ppa:nom/depot` les ajoute en une commande. Pratiques, mais même remarque que ci-dessus : la confiance repose sur la personne qui maintient le PPA.

## 6. Maîtriser les versions

### Voir les versions disponibles

```bash
apt-cache policy nginx
```

```
nginx:
  Installed: 1.24.0-2ubuntu7
  Candidate: 1.24.0-2ubuntu7.1
  Version table:
     1.24.0-2ubuntu7.1 500
        500 http://archive.ubuntu.com/ubuntu noble-updates/main amd64 Packages
 *** 1.24.0-2ubuntu7 500
        500 http://archive.ubuntu.com/ubuntu noble/main amd64 Packages
```

`Installed` est la version en place, `Candidate` celle qu'installerait un `upgrade`. Le nombre (500) est la priorité du dépôt.

### Installer une version précise

```bash
sudo apt install nginx=1.24.0-2ubuntu7
```

### Bloquer un paquet

Quand une mise à jour d'un composant critique doit être planifiée et testée (base de données, noyau, runtime de l'application), on peut empêcher sa mise à jour automatique :

```bash
sudo apt-mark hold postgresql-16       # bloquer
apt-mark showhold                      # lister les paquets bloqués
sudo apt-mark unhold postgresql-16     # débloquer
```

### Paquets installés manuellement ou automatiquement

`apt` distingue les paquets que vous avez demandés explicitement de ceux installés comme dépendances. C'est ce qui permet à `autoremove` de savoir quoi nettoyer.

```bash
apt-mark showmanual                    # ce qui a été installé volontairement
apt-mark showauto | wc -l              # nombre de dépendances automatiques
```

`apt-mark showmanual` est une excellente base pour documenter ou reproduire la configuration d'un serveur.

## 7. Les mises à jour de sécurité

Appliquer les correctifs de sécurité est l'une des tâches les plus importantes, et les plus négligées, de l'administration système.

```bash
sudo apt update
apt list --upgradable
sudo apt upgrade
```

### Les mises à jour automatiques

Ubuntu fournit `unattended-upgrades`, qui installe automatiquement les correctifs de sécurité :

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
cat /etc/apt/apt.conf.d/50unattended-upgrades     # ce qui est mis à jour automatiquement
less /var/log/unattended-upgrades/unattended-upgrades.log
```

Par défaut, seules les mises à jour issues de `-security` sont appliquées automatiquement, ce qui limite le risque de régression.

### Après la mise à jour : redémarrer ?

Mettre à jour un paquet remplace ses fichiers sur le disque, mais les processus déjà lancés continuent d'utiliser l'ancienne version en mémoire. Une bibliothèque de sécurité comme OpenSSL mise à jour ne protège réellement qu'une fois les services qui l'utilisent redémarrés.

```bash
cat /var/run/reboot-required 2>/dev/null     # présent si un redémarrage est nécessaire (nouveau noyau...)
cat /var/run/reboot-required.pkgs 2>/dev/null
sudo apt install needrestart
sudo needrestart                               # quels services utilisent une version périmée
```

### L'historique

Qui a installé quoi, et quand ? `apt` et `dpkg` gardent tout :

```bash
less /var/log/apt/history.log                  # commandes apt, avec date et utilisateur
grep " install " /var/log/dpkg.log             # chaque paquet installé
zgrep "Commandline" /var/log/apt/history.log*  # y compris les logs archivés
```

C'est souvent la première chose à regarder quand un serveur « s'est mis à dysfonctionner depuis hier ».

## 8. Les autres distributions

Les concepts sont identiques partout. Seules les commandes changent.

| Action | Ubuntu / Debian | RHEL / Rocky / Fedora | Alpine |
|---|---|---|---|
| Rafraîchir l'index | `apt update` | automatique (ou `dnf makecache`) | `apk update` |
| Mettre à jour le système | `apt upgrade` | `dnf upgrade` | `apk upgrade` |
| Installer | `apt install pkg` | `dnf install pkg` | `apk add pkg` |
| Supprimer | `apt remove pkg` | `dnf remove pkg` | `apk del pkg` |
| Chercher | `apt search mot` | `dnf search mot` | `apk search mot` |
| Informations | `apt show pkg` | `dnf info pkg` | `apk info pkg` |
| Paquets installés | `dpkg -l` | `rpm -qa` | `apk info` |
| Fichiers d'un paquet | `dpkg -L pkg` | `rpm -ql pkg` | `apk info -L pkg` |
| Paquet d'un fichier installé | `dpkg -S fichier` | `rpm -qf fichier` | `apk info --who-owns fichier` |
| Paquet fournissant un fichier | `apt-file search` | `dnf provides fichier` | `apk search cmd:nom` |
| Historique | `/var/log/apt/history.log` | `dnf history` | — |
| Dépôts | `/etc/apt/sources.list.d/` | `/etc/yum.repos.d/` | `/etc/apk/repositories` |

Les noms des paquets diffèrent aussi parfois d'une famille à l'autre : les en-têtes de développement s'appellent `libssl-dev` sous Debian et `openssl-devel` sous Red Hat, le serveur web Apache s'appelle `apache2` d'un côté et `httpd` de l'autre.

> 💡 Sur la famille Red Hat, de nombreux paquets courants se trouvent dans le dépôt complémentaire **EPEL**, à activer avec `dnf install epel-release`.

## 9. Autres façons d'installer des logiciels

### Snap et Flatpak

**Snap** (poussé par Canonical) et **Flatpak** distribuent des applications autonomes qui embarquent leurs dépendances et se mettent à jour indépendamment de la distribution. Ubuntu installe certains logiciels via snap par défaut. Utiles sur un poste de travail, ils sont moins courants sur les serveurs.

```bash
snap list
```

> 💡 Dans WSL, `snap` fonctionne uniquement si systemd est activé.

### Binaires et installation depuis les sources

Certains outils sont distribués sous forme d'un simple binaire ou d'une archive. La convention est de placer ce que l'on installe manuellement en dehors des chemins gérés par le gestionnaire de paquets :

| Emplacement | Usage |
|---|---|
| `/usr/local/bin` | Binaires installés manuellement pour tous les utilisateurs |
| `/opt/<logiciel>` | Logiciel autonome livré avec tous ses fichiers |
| `~/.local/bin` | Binaires installés pour un seul utilisateur |

Ne placez jamais rien à la main dans `/usr/bin` : c'est le territoire du gestionnaire de paquets, qui peut écraser vos fichiers lors d'une mise à jour.

### Le cas `curl | bash`

De nombreux outils proposent une installation en une ligne :

```bash
curl -fsSL https://exemple.com/install.sh | sudo bash
```

C'est pratique, mais cela revient à exécuter en root un script que vous n'avez pas lu, téléchargé depuis Internet. Sur un poste de développement, c'est parfois acceptable pour un éditeur de confiance. Sur un serveur, téléchargez d'abord le script, lisez-le, et préférez un dépôt officiel quand il existe.

## 10. Les gestionnaires de paquets des langages

Les développeurs utilisent aussi `pip`, `npm`, `gem`, `cargo`... Ces outils cohabitent avec le gestionnaire du système, et le mélange des deux cause des problèmes classiques.

### Python et `pip`

Depuis Ubuntu 23.04, lancer `pip install` en dehors d'un environnement virtuel produit une erreur :

```
error: externally-managed-environment
× This environment is externally managed
```

C'est volontaire (norme PEP 668) : le Python du système est utilisé par des outils de la distribution elle-même. Installer ou mettre à jour des bibliothèques par-dessus avec `pip`, surtout avec `sudo`, peut casser ces outils. Les bonnes pratiques :

```bash
# Pour un projet : un environnement virtuel
python3 -m venv .venv
source .venv/bin/activate
pip install requests

# Pour un outil en ligne de commande : pipx, qui isole chaque outil
sudo apt install pipx
pipx install httpie

# Pour une bibliothèque utilisée par des scripts système : le paquet de la distribution
sudo apt install python3-requests
```

> ⚠️ L'option `--break-system-packages` supprime l'erreur. Son nom dit clairement ce qu'elle risque de faire : elle n'a sa place que dans un conteneur jetable.

### Node.js et `npm`

La version de Node.js des dépôts Ubuntu est souvent ancienne. On installe généralement une version récente via le dépôt de NodeSource ou via un gestionnaire de versions comme `nvm`, qui installe Node dans le home de l'utilisateur. Dans les deux cas, évitez `sudo npm install -g` : installez les outils globaux dans un préfixe appartenant à votre utilisateur (ce que fait `nvm` automatiquement).

## 11. Les paquets dans un Dockerfile

Les images Docker basées sur Ubuntu ou Debian utilisent `apt-get`. Quelques règles donnent des images plus petites, plus rapides à construire et reproductibles :

```dockerfile
FROM ubuntu:24.04

RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      ca-certificates \
      curl \
      python3 \
 && rm -rf /var/lib/apt/lists/*
```

| Règle | Pourquoi |
|---|---|
| `update` et `install` dans **le même `RUN`** | Chaque `RUN` crée une couche mise en cache. Un `RUN apt-get update` séparé serait mis en cache et réutilisé tel quel lors des builds suivants, avec un index périmé qui finit par provoquer des erreurs 404 |
| `-y` | Pas de confirmation interactive possible pendant un build |
| `--no-install-recommends` | Évite d'installer des dizaines de paquets inutiles |
| `rm -rf /var/lib/apt/lists/*` | Supprime l'index téléchargé, inutile dans l'image finale (plusieurs dizaines de Mo) |
| Un paquet par ligne, trié | Lisibilité et relectures de code facilitées |
| `ca-certificates` | Souvent oublié : sans lui, les connexions HTTPS échouent avec `--no-install-recommends` |

> 💡 Pour des builds reproductibles, on peut fixer les versions des paquets critiques (`curl=8.5.0-2ubuntu10.6`), au prix d'une maintenance plus lourde : une version ancienne finit par disparaître des dépôts.

## 12. Exercices

### Exercice 7.1 — Les bases d'`apt` (niveau de base)

Dans l'Ubuntu WSL :

1. Mettez à jour l'index des paquets, puis listez les paquets qui peuvent être mis à jour.
2. Cherchez un outil permettant de manipuler du JSON en ligne de commande, et affichez ses informations (version, dépendances, taille).
3. Installez-le, ainsi que `cowsay`, en une seule commande. Vérifiez qu'ils fonctionnent : `echo '{"nom":"Alice","age":32}' | jq .nom` et `cowsay Bonjour`.
4. Listez les fichiers installés par `cowsay`. Où se trouve la commande ?
5. Supprimez `cowsay` avec `remove`, puis vérifiez son état avec `dpkg -l`. Faites la même chose avec `purge`. Quelle différence voyez-vous ?

<details>
<summary>Solution</summary>

```bash
sudo apt update
apt list --upgradable
apt search json | grep -i processor
apt show jq
sudo apt install jq cowsay
echo '{"nom":"Alice","age":32}' | jq .nom
cowsay Bonjour
dpkg -L cowsay | grep bin          # /usr/games/cowsay
sudo apt remove cowsay
dpkg -l cowsay                     # rc : supprimé, configuration conservée
sudo apt purge cowsay
dpkg -l cowsay                     # plus aucune trace
sudo apt autoremove
```

`cowsay` n'a pas de fichier de configuration à proprement parler : selon la version, l'état `rc` peut ne pas apparaître. Refaites l'essai avec un paquet qui en a, comme `nginx` dans un conteneur, pour voir clairement la différence.

</details>

### Exercice 7.2 — Enquêter sur les paquets (niveau de base)

Dans l'Ubuntu WSL :

1. Quel paquet fournit la commande `ls` ? Et la commande `curl` ?
2. Combien de paquets sont installés au total ? Combien l'ont été volontairement ?
3. Quel paquet faudrait-il installer pour obtenir la commande `dig` ? Trouvez-le de deux façons différentes.
4. Quels paquets ont été installés aujourd'hui ?

<details>
<summary>Solution</summary>

```bash
dpkg -S "$(readlink -f "$(command -v ls)")"     # coreutils
dpkg -S "$(readlink -f "$(command -v curl)")"   # curl

dpkg -l | grep -c "^ii"
apt-mark showmanual | wc -l

dig                                             # la suggestion d'Ubuntu
sudo apt install -y apt-file && sudo apt-file update
apt-file search bin/dig

grep "$(date +%F)" /var/log/dpkg.log | grep " install "
```

</details>

### Exercice 7.3 — Nettoyer après soi (niveau intermédiaire)

Dans un conteneur jetable :

```bash
docker run -it --rm ubuntu:24.04 bash
```

1. Mettez à jour l'index, puis notez le nombre de paquets installés.
2. Installez `nginx` normalement. Combien de paquets ont été ajoutés ?
3. Supprimez `nginx` avec `purge`. Tous les paquets ajoutés ont-ils disparu ? Faites le ménage.
4. Réinstallez `nginx` avec `--no-install-recommends`. Combien de paquets cette fois ?

<details>
<summary>Solution</summary>

```bash
apt-get update
dpkg -l | grep -c "^ii"
apt-get install -y nginx
dpkg -l | grep -c "^ii"
apt-get purge -y nginx
dpkg -l | grep -c "^ii"            # les dépendances sont toujours là
apt-get autoremove -y --purge
dpkg -l | grep -c "^ii"            # retour au nombre initial
apt-get install -y --no-install-recommends nginx
dpkg -l | grep -c "^ii"
```

`purge` ne supprime que le paquet demandé. Les dépendances installées automatiquement restent en place jusqu'à un `autoremove`.

</details>

### Exercice 7.4 — Bloquer une version (niveau intermédiaire)

Dans un conteneur jetable `ubuntu:24.04` :

1. Mettez à jour l'index, puis affichez la version installée et la version candidate de `libc-bin` et de `tar`.
2. Bloquez `tar`, puis lancez `apt-get upgrade -s` (simulation). `tar` fait-il partie des paquets qui seraient mis à jour ?
3. Débloquez-le et vérifiez.

<details>
<summary>Solution</summary>

```bash
apt-get update
apt-cache policy libc-bin tar
apt-mark hold tar
apt-mark showhold
apt-get upgrade -s | grep -E "^Inst|held back"
apt-mark unhold tar
apt-get upgrade -s | grep tar
```

L'option `-s` simule l'opération sans rien modifier : très pratique pour savoir ce qu'une mise à jour va changer. Si l'image Docker est très récente, il se peut qu'aucune mise à jour ne soit disponible pour `tar` : essayez avec un autre paquet de la liste `apt list --upgradable`.

</details>

### Exercice 7.5 — Ajouter un dépôt tiers (niveau intermédiaire)

Dans un conteneur du lab (`docker compose exec web bash`), installez l'outil GitHub CLI (`gh`) depuis le dépôt officiel de GitHub, en suivant la méthode moderne avec `signed-by`. Vérifiez ensuite :

1. que `gh --version` fonctionne ;
2. de quel dépôt provient le paquet installé ;
3. que la clé n'a pas été ajoutée au trousseau global (`apt-key list` ne doit pas la montrer, ou la commande n'existe plus).

<details>
<summary>Solution</summary>

```bash
apt-get update && apt-get install -y curl ca-certificates
mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg \
  -o /etc/apt/keyrings/githubcli-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
  > /etc/apt/sources.list.d/github-cli.list
apt-get update
apt-get install -y gh

gh --version
apt-cache policy gh              # la ligne du dépôt cli.github.com apparaît
ls /etc/apt/keyrings/
```

</details>

### Exercice 7.6 — Tour des distributions (niveau intermédiaire)

Dans un conteneur Rocky Linux puis dans un conteneur Alpine :

```bash
docker run -it --rm rockylinux:9 bash
docker run -it --rm alpine:3 sh
```

Dans chacun :

1. identifiez la distribution et sa version ;
2. installez `curl` et `jq` ;
3. trouvez quel paquet fournit la commande `ls` ;
4. comptez le nombre de paquets installés ;
5. comparez avec Ubuntu. Que remarquez-vous sur Alpine ?

<details>
<summary>Solution</summary>

Rocky Linux :

```bash
cat /etc/os-release
dnf install -y jq                 # curl est déjà présent (curl-minimal)
rpm -qf "$(readlink -f "$(command -v ls)")"    # coreutils
rpm -qa | wc -l
dnf provides '*/bin/dig'          # bind-utils
```

Alpine :

```bash
cat /etc/os-release
apk add curl jq
ls -l "$(command -v ls)"          # lien vers /bin/busybox
apk info --who-owns /bin/busybox  # busybox
apk info | wc -l
```

Sur Alpine, la plupart des commandes de base ne sont pas des programmes séparés mais des liens vers un seul binaire, **BusyBox**, qui les implémente toutes dans une version simplifiée. C'est ce qui rend l'image si petite, mais certaines options habituelles des commandes GNU manquent.

</details>

### Exercice 7.7 — Bonus : `pip` et l'environnement système

Dans l'Ubuntu WSL :

1. Essayez `pip install requests` (installez d'abord `python3-pip` si nécessaire). Lisez attentivement le message d'erreur.
2. Créez un environnement virtuel dans `~/projet-py`, activez-le, installez `requests`, et vérifiez d'où Python charge le module.
3. Installez l'outil `httpie` avec `pipx`, et vérifiez où il a été installé.

<details>
<summary>Solution</summary>

```bash
sudo apt install -y python3-pip python3-venv pipx
pip install requests                    # error: externally-managed-environment

mkdir -p ~/projet-py && cd ~/projet-py
python3 -m venv .venv
source .venv/bin/activate
pip install requests
python -c "import requests; print(requests.__file__)"   # dans .venv/
deactivate

pipx install httpie
pipx ensurepath                         # ajoute ~/.local/bin au PATH si besoin
which http                              # ~/.local/bin/http
http --version
```

</details>
