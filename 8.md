# Chapitre 8 — systemd et services

## 1. Le rôle de systemd

Au démarrage, le noyau lance un seul programme : le **PID 1**. Ce programme est chargé de démarrer tout le reste du système (montage des disques, réseau, journalisation, services), puis de surveiller les services pendant toute la vie de la machine et de les arrêter proprement à l'extinction. Il adopte aussi les processus orphelins (chapitre 5).

Sur la quasi-totalité des distributions modernes, ce PID 1 est **systemd**. Il a remplacé les anciens scripts de démarrage (*SysV init*, les scripts de `/etc/init.d/`), et apporte :

- le démarrage des services **en parallèle**, en respectant leurs dépendances ;
- la **surveillance** des services, avec redémarrage automatique en cas de plantage ;
- une **journalisation centralisée** de tous les services (`journald`) ;
- une configuration **déclarative** : on décrit ce qu'on veut, plutôt que d'écrire un script qui le fait ;
- des mécanismes d'**isolation** et de sécurité intégrés.

> 💡 systemd est une suite d'outils plus qu'un programme unique : `systemctl`, `journalctl`, `hostnamectl`, `timedatectl`, `loginctl`, `systemd-resolved`... Ce chapitre se concentre sur les services, les logs et les timers.

## 2. Les unités

systemd gère des objets appelés **unités** (*units*). Chaque unité est décrite par un fichier texte dont l'extension indique le type :

| Type | Extension | Rôle | Exemple |
|---|---|---|---|
| Service | `.service` | Un programme à lancer et surveiller | `nginx.service`, `ssh.service` |
| Timer | `.timer` | Déclencher un service à une date ou un intervalle | `apt-daily.timer` |
| Target | `.target` | Un groupe d'unités, un « état » du système | `multi-user.target` |
| Socket | `.socket` | Démarrer un service à la première connexion | `ssh.socket` |
| Mount | `.mount` | Un point de montage | `home.mount` |
| Path | `.path` | Déclencher un service quand un fichier change | |

### Où sont les fichiers d'unité ?

| Emplacement | Contenu | Qui le modifie ? |
|---|---|---|
| `/usr/lib/systemd/system/` (ou `/lib/systemd/system/`) | Unités installées par les paquets | Le gestionnaire de paquets. **Ne pas modifier** : vos changements seraient écrasés à la prochaine mise à jour |
| `/etc/systemd/system/` | Unités créées ou surchargées par l'administrateur | **Vous** |
| `/run/systemd/system/` | Unités générées à l'exécution | systemd |

Un fichier de `/etc/systemd/system/` est **prioritaire** sur un fichier du même nom dans `/usr/lib/systemd/system/`.

### Les targets

Les targets remplacent les anciens « niveaux d'exécution » (*runlevels*). Ce sont des points de rendez-vous qui regroupent des unités :

| Target | Signification |
|---|---|
| `multi-user.target` | Système complet en mode texte, avec réseau et services : l'état normal d'un serveur |
| `graphical.target` | Idem, plus l'interface graphique : l'état normal d'un poste de travail |
| `rescue.target` | Mode de secours, minimal |
| `network-online.target` | Le réseau est configuré et opérationnel |
| `timers.target` | Regroupe les timers |

```bash
systemctl get-default          # target atteinte au démarrage
```

## 3. Piloter les services avec `systemctl`

### Démarrer, arrêter, recharger

```bash
sudo systemctl start nginx       # démarrer
sudo systemctl stop nginx        # arrêter
sudo systemctl restart nginx     # arrêter puis redémarrer
sudo systemctl reload nginx      # recharger la configuration sans arrêter le service
sudo systemctl reload-or-restart nginx   # reload si possible, sinon restart
```

La différence entre `restart` et `reload` compte en production. `restart` coupe le service : les connexions en cours sont interrompues. `reload` demande au service de relire sa configuration sans s'arrêter (généralement en lui envoyant `SIGHUP`, chapitre 5). Tous les services ne savent pas faire de `reload` ; quand c'est possible, c'est la méthode à privilégier.

> 💡 Pour nginx, Apache et de nombreux serveurs, testez **toujours** la configuration avant de recharger : `sudo nginx -t`. Un `reload` avec une configuration invalide est refusé et l'ancienne configuration reste en place, mais un `restart` avec une configuration invalide arrête le service et l'empêche de redémarrer.

### Activer au démarrage

Démarrer un service et l'activer sont deux choses **indépendantes** :

```bash
sudo systemctl enable nginx      # démarrera automatiquement au prochain boot (ne le démarre pas maintenant)
sudo systemctl disable nginx     # ne démarrera plus au boot (ne l'arrête pas maintenant)
sudo systemctl enable --now nginx    # activer ET démarrer
sudo systemctl disable --now nginx   # désactiver ET arrêter
```

| | Démarré maintenant | Arrêté maintenant |
|---|---|---|
| **Activé** au boot | Situation normale d'un service en production | Il a planté, ou quelqu'un l'a arrêté à la main |
| **Désactivé** au boot | Démarré à la main : il ne reviendra pas après un redémarrage | Service inutilisé |

> ⚠️ Un oubli classique : démarrer un nouveau service avec `start`, vérifier qu'il fonctionne, et oublier `enable`. Tout va bien jusqu'au prochain redémarrage du serveur, parfois des mois plus tard.

### Masquer

`disable` n'empêche pas un service d'être démarré à la main ou comme dépendance d'un autre. `mask` l'interdit complètement :

```bash
sudo systemctl mask apache2      # impossible à démarrer, même manuellement
sudo systemctl unmask apache2
```

### Consulter l'état

```bash
systemctl status nginx
systemctl is-active nginx        # active / inactive / failed (pratique dans un script)
systemctl is-enabled nginx       # enabled / disabled / masked
systemctl is-failed nginx
```

Lire la sortie de `systemctl status` :


| Ligne | Ce qu'elle dit |

### Lister

```bash
systemctl list-units --type=service              # services chargés
systemctl list-units --type=service --state=running
systemctl --failed                               # unités en échec : la première commande à lancer sur un serveur qui va mal
systemctl list-unit-files --type=service         # tous les services installés et leur état d'activation
systemctl list-dependencies nginx                # dépendances
```

### Lire la définition d'un service

```bash
systemctl cat nginx                              # le fichier d'unité, et ses surcharges éventuelles
systemctl show nginx                             # toutes les propriétés effectives
systemctl show nginx -p MainPID -p Restart -p User
```

## 4. Les logs avec `journalctl`

`journald` collecte tout ce que les services écrivent sur leur sortie standard et leur sortie d'erreur, ainsi que les messages du noyau et du système. Plus besoin de chercher dans quel fichier de `/var/log` un service écrit : tout est au même endroit, horodaté et indexé.

### Filtrer par service

```bash
journalctl -u nginx                  # tous les logs de nginx
journalctl -u nginx -n 50            # les 50 dernières lignes
journalctl -u nginx -f               # suivre en direct (comme tail -f)
journalctl -u nginx -u php8.3-fpm    # plusieurs services
journalctl -u nginx -e               # ouvre directement à la fin
```

### Filtrer par date

```bash
journalctl --since "2026-09-15 14:00" --until "2026-09-15 15:00"
journalctl --since "1 hour ago"
journalctl --since today
journalctl --since yesterday --until today
```

### Filtrer par gravité

Chaque message a une priorité, de 0 (`emerg`) à 7 (`debug`) : `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`.

```bash
journalctl -p err                    # erreurs et plus grave
journalctl -p warning --since today
journalctl -u nginx -p err -b        # erreurs de nginx depuis le démarrage
```

### Autres filtres utiles

```bash
journalctl -b                        # depuis le démarrage actuel
journalctl -b -1                     # pendant le démarrage précédent (si les logs sont persistants)
journalctl --list-boots              # liste des démarrages enregistrés
journalctl -k                        # messages du noyau (équivalent de dmesg)
journalctl -t monscript              # messages envoyés avec logger -t monscript (chapitre 6)
journalctl _PID=1234                 # messages d'un processus précis
journalctl -u nginx -g "error|denied"    # filtrer le texte (expression régulière)
```

### Format de sortie

```bash
journalctl -u nginx -o cat           # le message seul, sans date ni nom de machine
journalctl -u nginx -o json-pretty   # tous les champs, en JSON
journalctl -u nginx --no-pager | grep ...   # pour enchaîner avec les outils du chapitre 3
```

### Espace disque et persistance

```bash
journalctl --disk-usage
sudo journalctl --vacuum-time=2weeks     # supprimer les logs de plus de deux semaines
sudo journalctl --vacuum-size=500M       # limiter la taille totale
```

Les logs sont persistants (ils survivent à un redémarrage) si le dossier `/var/log/journal/` existe, ce qui est le cas par défaut sur Ubuntu. La configuration se trouve dans `/etc/systemd/journald.conf`.

> 💡 Les fichiers de `/var/log/` (comme `/var/log/nginx/access.log`) existent toujours : certains services écrivent directement dans leurs propres fichiers. Le journal et les fichiers classiques cohabitent.

## 5. Écrire son propre service

C'est le cœur du chapitre. Plutôt que de lancer une application avec `nohup` ou dans un `tmux` (chapitre 5), on la confie à systemd, qui la démarre au boot, la surveille, la redémarre si elle plante, collecte ses logs et l'arrête proprement.

### Un premier fichier d'unité

`/etc/systemd/system/monapp.service` :

```ini
[Unit]
Description=monapp - application de démonstration
After=network.target

[Service]
Type=exec
User=monapp
Group=monapp
WorkingDirectory=/opt/monapp
ExecStart=/usr/bin/python3 /opt/monapp/app.py
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Le fichier est découpé en trois sections.

### La section `[Unit]` : description et dépendances

| Directive | Rôle |
|---|---|
| `Description` | Texte affiché par `systemctl status` et dans les logs |
| `After=` | **Ordre** de démarrage : démarrer après ces unités si elles doivent démarrer. Ne les démarre pas |
| `Wants=` | **Dépendance souple** : démarrer aussi ces unités, mais continuer même si elles échouent |
| `Requires=` | **Dépendance forte** : démarrer aussi ces unités ; si elles échouent ou s'arrêtent, ce service aussi |
| `StartLimitIntervalSec=`, `StartLimitBurst=` | Limite de redémarrages (voir plus bas) |

> ⚠️ `After` et `Wants`/`Requires` sont **indépendants** et se combinent souvent. `Requires=postgresql.service` seul démarre les deux services en même temps ; il faut ajouter `After=postgresql.service` pour attendre que la base soit démarrée. Pour une application qui a vraiment besoin du réseau, on utilise `Wants=network-online.target` et `After=network-online.target`.

### La section `[Service]` : comment lancer le programme

| Directive | Rôle |
|---|---|
| `Type=` | Comment systemd sait que le service a démarré (voir ci-dessous) |
| `ExecStart=` | La commande à lancer, avec un **chemin absolu** vers l'exécutable |
| `ExecStartPre=`, `ExecStartPost=` | Commandes à lancer avant ou après le démarrage (vérification de configuration, migration...) |
| `ExecReload=` | Commande pour recharger, par exemple `/bin/kill -HUP $MAINPID` |
| `User=`, `Group=` | L'identité du processus. **Ne faites pas tourner vos applications en root** (chapitre 4) |
| `WorkingDirectory=` | Le dossier courant du processus |
| `Environment=` | Une variable d'environnement : `Environment=PORT=8000` |
| `EnvironmentFile=` | Un fichier de variables, une par ligne (`NOM=valeur`) |
| `Restart=` | Quand redémarrer automatiquement |
| `RestartSec=` | Délai avant redémarrage |
| `TimeoutStopSec=` | Temps laissé au service pour s'arrêter après `SIGTERM` avant `SIGKILL` (90 s par défaut) |

Les principaux types :

| `Type=` | Le service est considéré démarré... | Usage |
|---|---|---|
| `simple` | Dès que le processus est lancé | Valeur par défaut historique |
| `exec` | Dès que le programme a été exécuté avec succès | **Recommandé** pour une application qui reste au premier plan : une erreur de chemin est détectée immédiatement |
| `notify` | Quand le programme signale lui-même qu'il est prêt | Programmes compatibles (PostgreSQL, nginx récent...) |
| `oneshot` | Quand le programme s'est **terminé** | Tâches ponctuelles : scripts, sauvegardes |
| `forking` | Quand le processus lancé s'est dédoublé et que le parent s'est terminé | Anciens démons qui passent d'eux-mêmes en arrière-plan |

Les valeurs de `Restart=` :

| Valeur | Redémarre si... |
|---|---|
| `no` | Jamais (défaut) |
| `on-failure` | Code de sortie non nul, tué par un signal (hors `SIGTERM`...), ou délai dépassé. **Le choix habituel** |
| `always` | Dans tous les cas, même après une sortie normale |
| `on-abnormal` | Signal ou délai dépassé, mais pas un code de sortie non nul |

> 💡 **Votre application n'a pas besoin de passer en arrière-plan** (« daemoniser »), ni d'écrire un fichier PID, ni de gérer ses propres fichiers de log. Avec systemd, la bonne pratique est de rester au premier plan et d'écrire les logs sur stdout et stderr : `journald` s'occupe du reste.

### La section `[Install]` : l'activation

`WantedBy=multi-user.target` signifie : quand on fait `systemctl enable` sur ce service, l'attacher à `multi-user.target`, c'est-à-dire le démarrer lors d'un démarrage normal. Concrètement, `enable` crée un lien symbolique :

```bash
ls -l /etc/systemd/system/multi-user.target.wants/
```

### Appliquer les modifications

Après avoir créé ou modifié un fichier d'unité, systemd doit relire sa configuration :

```bash
sudo systemctl daemon-reload
```

> ⚠️ **Oublier `daemon-reload` est l'erreur la plus fréquente** : vous modifiez le fichier, redémarrez le service, et rien ne change. `systemctl status` vous le rappelle d'ailleurs avec l'avertissement *« The unit file changed on disk. Run 'systemctl daemon-reload' »*.

```bash
systemd-analyze verify /etc/systemd/system/monapp.service   # vérifier la syntaxe
```

### La limite de redémarrages

Un service qui plante en boucle serait redémarré indéfiniment, consommant des ressources et noyant les logs. Par défaut, si un service démarre plus de 5 fois en 10 secondes, systemd abandonne et le laisse dans l'état `failed` avec la raison `start-limit-hit`. On ajuste cette limite dans la section `[Unit]` :

```ini
[Unit]
StartLimitIntervalSec=60
StartLimitBurst=3
```

Après avoir corrigé le problème, il faut réinitialiser le compteur :

```bash
sudo systemctl reset-failed monapp
sudo systemctl start monapp
```

### Le piège du tampon de sortie

Certains langages, dont Python, mettent leur sortie en **tampon** quand elle n'est pas un terminal. Sous systemd, les messages de l'application peuvent alors apparaître dans le journal avec un retard important, ou être perdus en cas de plantage. Solutions : forcer l'écriture dans le code (`print(..., flush=True)`), ou désactiver le tampon avec `Environment=PYTHONUNBUFFERED=1`.

## 6. Durcir un service

systemd peut restreindre ce qu'un service a le droit de faire, sans modifier son code. Ces directives réduisent fortement les dégâts possibles en cas de faille dans l'application.

| Directive | Effet |
|---|---|
| `NoNewPrivileges=yes` | Le service et ses enfants ne peuvent jamais gagner de privilèges (setuid, etc.) |
| `ProtectSystem=strict` | Tout le système de fichiers est en **lecture seule** pour le service |
| `ReadWritePaths=/var/lib/monapp` | Exceptions : dossiers où le service peut écrire |
| `ProtectHome=yes` | `/home`, `/root` et `/run/user` sont invisibles |
| `PrivateTmp=yes` | Le service a son propre `/tmp`, isolé des autres |
| `PrivateDevices=yes` | Pas d'accès aux périphériques physiques |
| `ProtectKernelTunables=yes` | Pas de modification des paramètres du noyau |
| `ProtectKernelModules=yes` | Pas de chargement de modules noyau |
| `ProtectControlGroups=yes` | Pas de modification des cgroups |
| `RestrictSUIDSGID=yes` | Pas de création de fichiers setuid ou setgid |
| `DynamicUser=yes` | systemd crée un utilisateur temporaire pour la durée du service |

systemd note lui-même l'exposition de chaque service :

```bash
systemd-analyze security                 # tous les services, avec un score d'exposition
systemd-analyze security monapp          # le détail pour un service
```

Le score va de 0 (très protégé) à 10 (aucune protection). La plupart des services installés par défaut sont très mal notés : c'est normal, les éditeurs restent prudents pour ne rien casser.

> 💡 Ajoutez les protections une par une et testez à chaque étape : si le service ne démarre plus, le journal indique généralement quel accès a été refusé.

## 7. Surcharger un service existant

Pour modifier un service installé par un paquet, on ne touche **jamais** au fichier de `/usr/lib/systemd/system/` : il serait écrasé à la prochaine mise à jour. On crée une **surcharge** (*drop-in*), un petit fichier qui ne contient que les directives à modifier :

```bash
sudo systemctl edit nginx
```

Cette commande ouvre un éditeur et crée `/etc/systemd/system/nginx.service.d/override.conf`. On n'y écrit que les changements :

```ini
[Service]
Restart=on-failure
RestartSec=5
```

À l'enregistrement, systemd effectue lui-même le `daemon-reload`. `systemctl cat nginx` affiche ensuite le fichier d'origine suivi de la surcharge.

> ⚠️ Les directives qui peuvent apparaître plusieurs fois, comme `ExecStart`, **s'additionnent** au lieu de se remplacer. Pour remplacer la commande de lancement, il faut d'abord la vider par une ligne `ExecStart=` vide :
>
> ```ini
> [Service]
> ExecStart=
> ExecStart=/usr/sbin/nginx -g "daemon off;"
> ```

> 💡 Autre subtilité : si une même variable est définie à la fois par `Environment=` et par `EnvironmentFile=`, c'est la valeur du **fichier** qui l'emporte. Une surcharge avec `Environment=` ne modifiera donc pas une variable déjà définie dans le fichier d'environnement.

```bash
sudo systemctl revert nginx      # supprimer toutes les surcharges et revenir à l'original
```

## 8. Les timers : l'alternative moderne à cron

Un **timer** déclenche un service à des moments précis. Il se compose de deux fichiers : un `.service` qui décrit **quoi** faire (généralement de type `oneshot`), et un `.timer` du même nom qui décrit **quand**.

`/etc/systemd/system/nettoyage.service` :

```ini
[Unit]
Description=Nettoyage des fichiers temporaires de l'application

[Service]
Type=oneshot
ExecStart=/usr/bin/find /tmp -name "monapp-*" -mtime +7 -delete
```

`/etc/systemd/system/nettoyage.timer` :

```ini
[Unit]
Description=Nettoyage quotidien

[Timer]
OnCalendar=daily
Persistent=true
RandomizedDelaySec=15min

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now nettoyage.timer      # on active le timer, pas le service
systemctl list-timers                            # prochaines et dernières exécutions
sudo systemctl start nettoyage.service           # lancer la tâche immédiatement, pour tester
journalctl -u nettoyage.service                  # le résultat
```

### La syntaxe `OnCalendar`

Le format général est `JourDeLaSemaine Année-Mois-Jour Heure:Minute:Seconde`, chaque partie étant facultative.

| Expression | Signification |
|---|---|
| `hourly`, `daily`, `weekly`, `monthly` | Raccourcis (à minuit pour `daily`) |
| `*-*-* 02:30:00` | Tous les jours à 2h30 |
| `Mon..Fri 09:00` | Du lundi au vendredi à 9h |
| `*:0/15` | Toutes les 15 minutes |
| `*-*-01 00:00:00` | Le 1er de chaque mois à minuit |
| `Sat,Sun 10:00` | Le week-end à 10h |

```bash
systemd-analyze calendar "Mon..Fri 09:00"        # vérifier et voir la prochaine occurrence
systemd-analyze calendar --iterations=5 "*:0/15"
```

D'autres déclencheurs existent, relatifs à des événements plutôt qu'au calendrier : `OnBootSec=5min` (5 minutes après le démarrage) et `OnUnitActiveSec=1h` (une heure après la dernière exécution).

### Timer ou cron ?

| | cron | Timer systemd |
|---|---|---|
| Simplicité | Une ligne | Deux fichiers |
| Logs | À rediriger soi-même | Automatiquement dans le journal |
| Environnement | Minimal et surprenant (chapitre 6) | Maîtrisé et explicite (`User`, `Environment`...) |
| Tâche manquée (machine éteinte) | Perdue | Rattrapée avec `Persistent=true` |
| Exécutions simultanées | Possibles si une exécution dure plus longtemps que l'intervalle | Impossibles : un service déjà actif n'est pas relancé |
| Isolation, limites de ressources, durcissement | Non | Toutes les options d'un service |
| Test manuel | Copier la commande | `systemctl start tache.service`, dans les conditions exactes |
| Répartir la charge | Non | `RandomizedDelaySec` |

cron reste parfaitement valable pour une tâche simple. Pour une tâche importante en production, le timer est plus robuste et bien plus facile à surveiller.

## 9. Les services utilisateur

Chaque utilisateur peut aussi gérer ses propres services, sans `sudo`, avec l'option `--user`. Les fichiers d'unité se placent dans `~/.config/systemd/user/`.

```bash
systemctl --user status
systemctl --user enable --now monoutil.service
journalctl --user -u monoutil
```

Par défaut, les services utilisateur s'arrêtent quand l'utilisateur se déconnecte. Pour qu'ils tournent en permanence : `sudo loginctl enable-linger student`.

## 11. Diagnostiquer un service qui ne démarre pas

La démarche, dans l'ordre :

1. **`systemctl status monapp`** : l'état, le code de sortie et les dernières lignes du journal. Souvent, la réponse est déjà là.
2. **`journalctl -u monapp -n 50 --no-pager`** : plus de contexte, notamment le message d'erreur de l'application elle-même.
3. **Lire le code de sortie.** Un code entre 200 et 243 est un code propre à systemd, qui indique l'étape qui a échoué **avant** même le lancement du programme :

| Code | Signification |
|---|---|
| `200/CHDIR` | Le `WorkingDirectory` n'existe pas ou n'est pas accessible |
| `203/EXEC` | L'exécutable de `ExecStart` est introuvable ou n'est pas exécutable |
| `217/USER` | L'utilisateur de `User=` n'existe pas |
| `226/NAMESPACE` | Un chemin indiqué dans une option de durcissement n'existe pas |
| `1`, `2`... | Le programme a démarré, puis s'est terminé en erreur : lire ses propres messages |

### Exercice 8.4 — Déployer son application comme un service (projet du chapitre)

Nous allons déployer une petite application web Python comme un vrai service de production.

**Étape 1 : préparer l'application.** Créez un utilisateur système dédié `monapp`, sans shell de connexion, puis le dossier `/opt/monapp` et le fichier `/opt/monapp/app.py` suivant :

```python
#!/usr/bin/env python3
"""monapp — une petite application web pour les exercices systemd."""
import json
import os
import pwd
import signal
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer

PORT = int(os.environ.get("PORT", "8000"))
MESSAGE = os.environ.get("MESSAGE", "Bonjour depuis monapp")


class Handler(BaseHTTPRequestHandler):
    def _send(self, code, data):
        body = json.dumps(data).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/health":
            self._send(200, {"status": "ok"})
        elif self.path == "/crash":
            print("Crash demandé : arrêt brutal avec le code 1", file=sys.stderr, flush=True)
            os._exit(1)
        else:
            self._send(200, {
                "message": MESSAGE,
                "pid": os.getpid(),
                "user": pwd.getpwuid(os.getuid()).pw_name,
                "cwd": os.getcwd(),
            })


def arret(signum, frame):
    print(f"Signal {signal.Signals(signum).name} reçu : arrêt propre", flush=True)
    sys.exit(0)


signal.signal(signal.SIGTERM, arret)
print(f"Démarrage de monapp sur le port {PORT}", flush=True)
HTTPServer(("0.0.0.0", PORT), Handler).serve_forever()
```

L'application lit son port et son message dans des variables d'environnement, répond en JSON, s'arrête proprement sur `SIGTERM`, et plante volontairement quand on appelle `/crash`.

**Étape 2 : la configuration.** Créez le fichier `/etc/monapp/monapp.env` avec `PORT=8000` et un message de votre choix. Ce fichier doit être lisible par l'application mais pas par les autres utilisateurs.

**Étape 3 : le service.** Écrivez `/etc/systemd/system/monapp.service` pour que l'application :

- tourne sous l'utilisateur `monapp`, dans le dossier `/opt/monapp` ;
- lise sa configuration dans `/etc/monapp/monapp.env` ;
- redémarre automatiquement en cas de plantage, après 3 secondes ;
- abandonne après 3 plantages en une minute ;
- démarre automatiquement au boot.

**Étape 4 : vérifier.** Démarrez et activez le service, puis vérifiez son état, ses logs, et que `curl localhost:8000` renvoie le bon message, le bon utilisateur et le bon dossier.

<details>
<summary>Solution</summary>

```bash
sudo useradd -r -s /usr/sbin/nologin -d /opt/monapp monapp
sudo mkdir -p /opt/monapp /etc/monapp
sudo nano /opt/monapp/app.py                    # coller le code
sudo chown -R root:monapp /opt/monapp
sudo chmod 750 /opt/monapp
sudo chmod 640 /opt/monapp/app.py

printf 'PORT=8000\nMESSAGE=Bonjour depuis systemd\n' | sudo tee /etc/monapp/monapp.env
sudo chown root:monapp /etc/monapp/monapp.env
sudo chmod 640 /etc/monapp/monapp.env
```

L'application et sa configuration appartiennent à root : le service peut les lire grâce à son groupe, mais ne peut pas les modifier. Si l'application était compromise, l'attaquant ne pourrait pas remplacer le code.

`/etc/systemd/system/monapp.service` :

```ini
[Unit]
Description=monapp - application de démonstration
After=network.target
StartLimitIntervalSec=60
StartLimitBurst=3

[Service]
Type=exec
User=monapp
Group=monapp
WorkingDirectory=/opt/monapp
EnvironmentFile=/etc/monapp/monapp.env
ExecStart=/usr/bin/python3 /opt/monapp/app.py
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash

sudo systemctl daemon-reload
sudo systemctl enable --now monapp
systemctl status monapp
journalctl -u monapp -n 20
curl -s localhost:8000 | jq
curl -s localhost:8000/health
```

</details>

### Exercice 8.5 — Tester la résilience (niveau intermédiaire)

Avec le service de l'exercice précédent :

1. Suivez les logs du service dans un terminal. Dans un autre, arrêtez-le avec `systemctl stop`. Que dit l'application ? Est-il redémarré ?
2. Redémarrez-le, puis provoquez un plantage avec `curl localhost:8000/crash`. Que se passe-t-il ? Le PID a-t-il changé ?
3. Tuez le processus principal avec `kill -9`. Et maintenant ?
4. Provoquez quatre plantages rapprochés, en moins d'une minute. Dans quel état est le service ? Remettez-le en marche.
5. Redémarrez complètement WSL (`wsl --shutdown` dans PowerShell, puis relancez Ubuntu). L'application est-elle revenue toute seule ?

<details>
<summary>Solution</summary>

```bash
journalctl -u monapp -f          # dans le premier terminal

sudo systemctl stop monapp       # « Signal SIGTERM reçu : arrêt propre », pas de redémarrage
sudo systemctl start monapp

curl localhost:8000/crash        # plantage, puis redémarrage 3 secondes plus tard
systemctl status monapp          # nouveau Main PID

sudo kill -9 "$(systemctl show monapp -p MainPID --value)"   # redémarrage également

for i in 1 2 3 4; do curl -s localhost:8000/crash; sleep 4; done
systemctl status monapp          # failed (Result: start-limit-hit)
sudo systemctl reset-failed monapp
sudo systemctl start monapp
```

Un arrêt avec `systemctl stop` n'est pas un échec : pas de redémarrage. Un code de sortie non nul ou un `SIGKILL` en sont un : `Restart=on-failure` relance le service. Au redémarrage de WSL, le service revient grâce à `enable`.

La limite compte les **démarrages** sur la fenêtre de 60 secondes : avec `StartLimitBurst=3`, trois redémarrages sont acceptés, le quatrième est refusé. Selon le moment du dernier démarrage manuel, trois plantages peuvent donc suffire, ou il en faut quatre.

</details>

### Exercice 8.7 — Réparer un service cassé (niveau intermédiaire)

Préparez un service volontairement défaillant :

```bash
sudo mkdir -p /opt/cassee
sudo cp /opt/monapp/app.py /opt/cassee/app.py
sudo chmod 600 /opt/cassee/app.py
printf 'PORT=8000\nMESSAGE=Je suis enfin réparé\n' | sudo tee /etc/cassee.env > /dev/null

sudo tee /etc/systemd/system/cassee.service > /dev/null << 'EOF'
[Unit]
Description=Un service qui ne veut pas démarrer

[Service]
Type=exec
User=appli
WorkingDirectory=/opt/cassee
EnvironmentFile=/etc/cassee/cassee.env
ExecStart=/usr/bin/python3 /opt/cassee/app.py
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl start cassee
```

Le service ne démarre pas. En appliquant la démarche de la section 11, trouvez et corrigez **tous** les problèmes, un par un, jusqu'à ce que `curl localhost:8001` renvoie « Je suis enfin réparé ». Le service doit tourner sous un utilisateur dédié `appli`, et l'application `monapp` doit continuer de fonctionner.

<details>
<summary>Solution</summary>

Il y a quatre problèmes, qui apparaissent successivement.

**1. L'utilisateur n'existe pas.** `systemctl status cassee` affiche `status=217/USER`.

```bash
sudo useradd -r -s /usr/sbin/nologin appli
```

**2. Le fichier d'environnement est introuvable.** Le journal indique `Failed to load environment files: No such file or directory` : le fichier a été créé dans `/etc/cassee.env` au lieu de `/etc/cassee/cassee.env`.

```bash
sudo mkdir -p /etc/cassee
sudo mv /etc/cassee.env /etc/cassee/cassee.env
sudo chown root:appli /etc/cassee/cassee.env
sudo chmod 640 /etc/cassee/cassee.env
```

**3. L'application n'est pas lisible.** Le programme démarre, puis Python échoue avec `Permission denied` sur `app.py` : le fichier est en `600`, propriété de root.

```bash
sudo chown -R root:appli /opt/cassee
sudo chmod 640 /opt/cassee/app.py
```

**4. Le port est déjà pris.** L'application échoue avec `Address already in use` : `monapp` utilise déjà le port 8000.

```bash
sudo sed -i 's/^PORT=8000/PORT=8001/' /etc/cassee/cassee.env
```

Puis, après chaque correction :

```bash
sudo systemctl reset-failed cassee
sudo systemctl restart cassee
systemctl status cassee
journalctl -u cassee -n 20 --no-pager
```

Et enfin :

```bash
curl -s localhost:8001 | jq
curl -s localhost:8000 | jq      # monapp fonctionne toujours
```

Les deux premiers problèmes empêchent systemd de lancer le programme : ils apparaissent dans les messages de systemd lui-même. Les deux derniers sont des erreurs de l'application : il faut lire ses propres messages dans le journal.

</details>
