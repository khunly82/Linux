# Chapitre 1 — Introduction et mise en place de l'environnement

## 1. Pourquoi Linux quand on est développeur ?

L'immense majorité des serveurs, des conteneurs et des environnements cloud tournent sous Linux. Même quand on développe sous Windows ou macOS, le code finit presque toujours par s'exécuter sur une machine Linux : un conteneur Docker, un runner de CI, une VM chez un cloud provider, un cluster Kubernetes.

Comprendre Linux, c'est donc pouvoir diagnostiquer soi-même pourquoi une application ne démarre pas en production, lire des logs, comprendre une erreur de permission, ou savoir pourquoi un port n'est pas joignable, au lieu de dépendre systématiquement d'une équipe ops.

---

## 2. Un peu d'histoire

En 1983, Richard Stallman lance le projet **GNU**, dont l'objectif est de créer un système d'exploitation entièrement libre compatible Unix. Le projet produit de nombreux outils (le compilateur `gcc`, le shell `bash`, les commandes de base comme `ls`, `cp`, `grep`...), mais il lui manque un noyau fonctionnel.

En 1991, Linus Torvalds, étudiant finlandais, publie un petit noyau qu'il appelle **Linux**. La combinaison du noyau Linux et des outils GNU donne un système complet. C'est pour cela que certains parlent de « GNU/Linux ».

Aujourd'hui, Linux est partout : serveurs, Android, routeurs, supercalculateurs (la totalité du classement TOP500), voitures, objets connectés.

---

## 3. Noyau et espace utilisateur

Un système Linux se découpe en deux grandes parties.

Le **noyau** (kernel) est le cœur du système. Il gère le matériel (processeur, mémoire, disques, réseau), décide quel processus s'exécute à quel moment, isole les processus les uns des autres et contrôle les accès. Il tourne dans un mode privilégié du processeur, appelé *espace noyau*.

L'**espace utilisateur** (userspace) regroupe tout le reste : le shell, les commandes, les services, vos applications. Ces programmes n'accèdent jamais directement au matériel. Quand ils ont besoin de lire un fichier, d'ouvrir une connexion réseau ou de créer un processus, ils le demandent au noyau via des **appels système** (syscalls) comme `open`, `read`, `write`, `fork` ou `connect`.

```
┌────────────────────────────────────────────┐
│  Espace utilisateur                        │
│  bash, python, nginx, votre application... │
├──────────────── appels système ────────────┤
│  Noyau Linux                               │
│  processus, mémoire, fichiers, réseau      │
├────────────────────────────────────────────┤
│  Matériel                                  │
└────────────────────────────────────────────┘
```

> 💡 **Lien avec Docker :** un conteneur n'est pas une VM. Tous les conteneurs d'une machine partagent le **même noyau**. Ce qui change d'un conteneur à l'autre, c'est uniquement l'espace utilisateur (les fichiers, les bibliothèques, les processus visibles). C'est pour ça qu'un conteneur démarre en une fraction de seconde.

### « Tout est fichier »

Un principe central hérité d'Unix : presque tout est représenté comme un fichier. Les fichiers classiques bien sûr, mais aussi les périphériques (`/dev/sda` pour un disque, `/dev/null` pour le « trou noir »), les informations sur les processus (`/proc/1234/`), ou les paramètres du noyau (`/proc/sys/`, `/sys/`).

Conséquence pratique : les mêmes outils (`cat`, `echo`, `grep`, redirections) permettent de lire un fichier texte, consulter l'état d'un processus ou modifier un paramètre du système.

```bash
cat /proc/cpuinfo        # informations sur le processeur
cat /proc/meminfo        # état de la mémoire
cat /proc/version        # version du noyau
```

## 4. Les distributions

Le noyau seul ne suffit pas. Une **distribution** assemble un noyau, des outils de base, un gestionnaire de paquets, un système d'initialisation (généralement systemd), une configuration par défaut et une politique de mises à jour.

Les grandes familles à connaître :

| Famille | Distributions | Gestionnaire de paquets | Format | Usage typique |
|---|---|---|---|---|
| Debian | Debian, Ubuntu, Linux Mint | `apt` | `.deb` | Serveurs, postes de travail, cloud |
| Red Hat | RHEL, Fedora, Rocky Linux, AlmaLinux | `dnf` (ex-`yum`) | `.rpm` | Entreprise, serveurs |
| Arch | Arch Linux, Manjaro | `pacman` | — | Postes de passionnés, rolling release |
| Alpine | Alpine Linux | `apk` | — | Images Docker légères |

Pour ce cours, nous utilisons **Ubuntu**. Ce que vous apprenez s'applique quasiment tel quel aux autres distributions : les commandes de base, les permissions, systemd, le réseau et SSH sont les mêmes partout. La principale différence est le gestionnaire de paquets et l'emplacement de certains fichiers de configuration.

> ⚠️ **Alpine** est très utilisée comme base d'images Docker car elle est minuscule (environ 5 Mo). Mais elle utilise `musl` au lieu de `glibc` et `busybox` au lieu des outils GNU : certaines commandes ont moins d'options, et certains binaires compilés ailleurs n'y fonctionnent pas. Bon à savoir quand un conteneur se comporte bizarrement.

### Savoir sur quelle distribution on est

```bash
cat /etc/os-release      # nom et version de la distribution
uname -r                 # version du noyau
uname -a                 # toutes les infos système
```

## 5. Notre environnement : WSL + Docker

Nous allons travailler avec deux outils complémentaires.

**WSL (Windows Subsystem for Linux)** fait tourner une vraie distribution Linux sous Windows. Depuis WSL2, il s'agit d'un **vrai noyau Linux** exécuté dans une machine virtuelle très légère gérée par Windows. Ce sera notre « serveur principal », sur lequel nous pourrons utiliser systemd, gérer des services et manipuler des disques.

**Docker** nous servira à simuler plusieurs machines sur un même réseau, pour travailler le réseau, SSH, le pare-feu et le diagnostic de pannes.

### 5.1 Vérifier WSL

Dans PowerShell (côté Windows) :

```powershell
wsl --version
wsl --list --verbose
```

La colonne `VERSION` doit indiquer `2`. Vous verrez probablement une distribution `docker-desktop` : elle est interne à Docker Desktop, **ne l'utilisez pas** pour le cours.

### 5.2 Installer Ubuntu

Si aucune distribution Ubuntu n'apparaît :

```powershell
wsl --install -d Ubuntu-24.04
```

Au premier lancement, Ubuntu demande de créer un nom d'utilisateur et un mot de passe. Ce compte n'a aucun lien avec votre compte Windows. **Retenez bien ce mot de passe**, il sera demandé à chaque utilisation de `sudo`.

Pour lancer Ubuntu ensuite, il suffit de taper `wsl` (ou `wsl -d Ubuntu-24.04`) dans PowerShell, ou de passer par Windows Terminal.

Première chose à faire une fois dedans, mettre le système à jour :

```bash
sudo apt update && sudo apt upgrade -y
```

### 5.3 Activer systemd

**systemd** est le premier programme lancé par le noyau au démarrage (il porte le numéro de processus 1). Il démarre et surveille tous les services du système. Nous l'utiliserons en détail au chapitre 8. Par défaut il peut être désactivé dans WSL, vérifions :

```bash
ps -p 1 -o comm=
```

Si la réponse est `systemd`, tout est bon. Sinon, créez ou éditez le fichier `/etc/wsl.conf` :

```bash
sudo nano /etc/wsl.conf
```

Avec ce contenu :

```ini
[boot]
systemd=true
```

Enregistrez (`Ctrl+O`, `Entrée`), quittez (`Ctrl+X`), puis **redémarrez WSL depuis PowerShell** :

```powershell
wsl --shutdown
```

Relancez Ubuntu et vérifiez à nouveau avec `ps -p 1 -o comm=`, puis :

```bash
systemctl status
```

La sortie doit afficher `State: running` (ou éventuellement `degraded`, ce qui est fréquent sous WSL et sans gravité pour le cours).

### 5.4 Fichiers Windows et fichiers Linux

Depuis Ubuntu, les disques Windows sont accessibles sous `/mnt/` :

```bash
ls /mnt/c/Users/
```

Depuis l'Explorateur Windows, les fichiers Linux sont accessibles via le chemin `\\wsl.localhost\Ubuntu-24.04\`.

> ⚠️ **Travaillez dans votre home Linux (`~`), pas dans `/mnt/c`.** L'accès aux fichiers Windows depuis Linux est beaucoup plus lent, et les permissions Linux n'y fonctionnent pas correctement. Tous les exercices du cours se font dans `~`.

### 5.5 Connecter Docker à Ubuntu

Dans Docker Desktop : **Settings → Resources → WSL Integration**, activez l'intégration pour votre distribution Ubuntu, puis cliquez sur *Apply & Restart*.

De retour dans Ubuntu :

```bash
docker version
docker run --rm hello-world
```

Si le message *Hello from Docker!* s'affiche, Docker est utilisable depuis Linux.

## 6. Le lab multi-machines

Nous allons créer un petit réseau de trois machines : un **bastion** (point d'entrée), un serveur **web** et un serveur **db**. Ce lab sera réutilisé aux chapitres 9, 10, 11 et 13.

### 6.1 Créer le dossier du lab

```bash
mkdir -p ~/lab && cd ~/lab
```

### 6.2 Le Dockerfile

Créez le fichier `~/lab/Dockerfile` :

```dockerfile
FROM ubuntu:24.04

# Réinstalle la documentation et les outils retirés de l'image minimale,
# puis installe les outils dont nous aurons besoin
RUN apt-get update && \
    apt-get install -y unminimize && yes | unminimize && \
    apt-get install -y openssh-server sudo iproute2 iputils-ping \
        dnsutils nftables curl vim nano less man-db procps \
        netcat-openbsd && \
    mkdir -p /run/sshd && ssh-keygen -A && \
    useradd -m -s /bin/bash -G sudo student && \
    echo 'student:student' | chpasswd

CMD ["/usr/sbin/sshd", "-D"]
```

Quelques explications. Les images Docker Ubuntu sont volontairement « minimisées » : pas de pages de manuel, peu d'outils. La commande `unminimize` restaure un système plus proche d'un vrai serveur. Nous installons ensuite le serveur SSH, des outils réseau et des éditeurs. Enfin, nous créons un utilisateur `student` (mot de passe `student`) membre du groupe `sudo`. Le conteneur lance le serveur SSH au premier plan (`-D`), ce qui le maintient en vie.

> 🔒 Un mot de passe identique au nom d'utilisateur est évidemment à proscrire en production. Nous le corrigerons au chapitre 10 en passant à l'authentification par clé.

### 6.3 Le fichier docker-compose.yml

Créez `~/lab/docker-compose.yml` :

```yaml
services:
  bastion:
    build: .
    hostname: bastion
    cap_add: [NET_ADMIN]
    ports:
      - "2222:22"

  web:
    build: .
    hostname: web
    cap_add: [NET_ADMIN]

  db:
    build: .
    hostname: db
    cap_add: [NET_ADMIN]
```

Les trois conteneurs sont placés automatiquement sur un même réseau Docker et peuvent se joindre par leur nom (`web`, `db`, `bastion`). Seul le bastion est exposé à l'extérieur, sur le port 2222. L'option `cap_add: [NET_ADMIN]` autorise la configuration réseau et le pare-feu à l'intérieur des conteneurs.

### 6.4 Démarrer le lab

```bash
cd ~/lab
docker compose up -d --build
docker compose ps
```

Le premier build prend quelques minutes (téléchargement et installation des paquets). Les trois services doivent apparaître avec l'état `running`.

### 6.5 Se connecter

Par SSH, via le bastion :

```bash
ssh -p 2222 student@localhost
```

Au premier accès, SSH demande de confirmer l'empreinte du serveur : répondez `yes`. Une fois sur le bastion, vous pouvez rebondir vers les autres machines :

```bash
ssh student@web
```

Si la connexion SSH pose problème, il est toujours possible d'ouvrir un shell directement dans un conteneur :

```bash
docker compose exec bastion bash
```

### 6.6 Commandes utiles pour gérer le lab

| Commande | Effet |
|---|---|
| `docker compose up -d` | Démarre le lab |
| `docker compose stop` | Arrête les conteneurs (leur contenu est conservé) |
| `docker compose down` | Supprime les conteneurs (retour à zéro) |
| `docker compose up -d --build` | Reconstruit l'image après modification du Dockerfile |
| `docker compose exec web bash` | Ouvre un shell root dans `web` |

> 💡 **Vous avez tout cassé ?** Aucun problème : `docker compose down && docker compose up -d` et vous repartez sur des machines neuves en quelques secondes. N'hésitez pas à expérimenter.

## 7. Exercices

### Exercice 1.1 — Découvrir son système (niveau de base)

Dans votre Ubuntu WSL, trouvez :

1. le nom et la version exacte de la distribution ;
2. la version du noyau ;
3. le nombre de cœurs de processeur visibles ;
4. la quantité de mémoire totale.

<details>
<summary>Solution</summary>

```bash
cat /etc/os-release
uname -r
nproc                       # ou : grep -c processor /proc/cpuinfo
grep MemTotal /proc/meminfo # ou : free -h
```

</details>

### Exercice 1.2 — Un noyau partagé (niveau intermédiaire)

Comparez la version du noyau dans WSL et dans un conteneur du lab. Que constatez-vous ? Comparez ensuite le contenu de `/etc/os-release`. Expliquez la différence.

<details>
<summary>Solution</summary>

```bash
uname -r
docker compose exec web uname -r
docker compose exec web cat /etc/os-release
```

La version du noyau est **identique** : WSL et les conteneurs partagent le même noyau Linux. Le fichier `/etc/os-release`, lui, vient de l'image du conteneur (l'espace utilisateur).

```bash
docker run --rm alpine sh -c 'uname -r; cat /etc/os-release'
```

</details>

### Exercice 1.3 — Explorer le lab (niveau intermédiaire)

Connectez-vous au bastion en SSH, puis rebondissez sur `web`. Depuis `web`, vérifiez que vous pouvez joindre `db` avec `ping`. Quelle est l'adresse IP de chaque machine ?

<details>
<summary>Solution</summary>

```bash
ssh -p 2222 student@localhost
ssh student@web
ping -c 3 db
ip a            # adresse IP de la machine courante
getent hosts db # résolution du nom db
```

</details>
