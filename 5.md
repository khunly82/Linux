# Chapitre 5 — Processus

> 💡 Ce chapitre se fait principalement **dans l'Ubuntu WSL**. Un conteneur ne montre que ses propres processus, ce qui est peu représentatif d'un vrai serveur.

Installez d'abord les outils utilisés dans ce chapitre :

```bash
sudo apt install -y htop lsof strace psmisc tmux
```

---

## 1. Qu'est-ce qu'un processus ?

Un **programme** est un fichier sur le disque : `/usr/bin/python3`, par exemple. Un **processus** est un programme **en cours d'exécution**, avec sa propre mémoire, ses fichiers ouverts, son identité (utilisateur et groupe) et son état. Lancer trois fois `python3`, c'est créer trois processus distincts à partir du même programme.

Chaque processus possède :

| Attribut | Description |
|---|---|
| **PID** | Identifiant unique du processus |
| **PPID** | PID du processus parent, celui qui l'a créé |
| **UID / GID** | Utilisateur et groupe sous lesquels il s'exécute (chapitre 4) |
| Dossier courant | Le dossier depuis lequel il travaille |
| Environnement | Ses variables d'environnement (`PATH`, `HOME`...) |
| Descripteurs de fichiers | Les fichiers, sockets et pipes qu'il a ouverts (stdin, stdout, stderr...) |

### Une arborescence de processus

Sous Linux, un processus est toujours créé par un autre processus. Quand vous tapez `ls` dans bash, bash se duplique (appel système `fork`), puis la copie se transforme en `ls` (appel système `exec`). Bash est donc le **parent** de `ls`.

Tous les processus descendent ainsi d'un ancêtre commun : le **PID 1**, lancé par le noyau au démarrage. Sur un système moderne, c'est **systemd**.

```bash
pstree -p          # l'arbre des processus avec leurs PID
pstree -p $$       # l'arbre à partir de votre shell
echo $$            # PID du shell courant
echo $PPID         # PID de son parent
```

```
systemd(1)─┬─cron(210)
           ├─sshd(305)───sshd(1402)───bash(1410)───pstree(1532)
           └─systemd-journal(98)
```

### Les états d'un processus

| État | Code | Signification |
|---|---|---|
| Running | `R` | En cours d'exécution ou prêt à s'exécuter |
| Sleeping | `S` | En attente d'un événement (entrée clavier, réseau, timer). C'est l'état de la grande majorité des processus |
| Uninterruptible | `D` | En attente d'une opération d'entrée/sortie qui ne peut pas être interrompue, souvent le disque ou le réseau (NFS). Beaucoup de processus en `D` signalent un problème de stockage |
| Stopped | `T` | Suspendu (par `Ctrl+Z` par exemple) |
| Zombie | `Z` | Terminé, mais son parent n'a pas encore récupéré son code de sortie |

**Les zombies** ne consomment ni CPU ni mémoire, seulement une entrée dans la table des processus. Ils sont le symptôme d'un parent mal programmé qui ne « récolte » pas ses enfants. On ne peut pas tuer un zombie (il est déjà mort) : il faut corriger ou tuer son parent.

**Les orphelins** sont des processus dont le parent s'est terminé. Ils sont automatiquement adoptés par le PID 1, qui se charge de les récolter à leur mort.

## 2. Lister les processus avec `ps`

### Les deux syntaxes classiques

```bash
ps                 # processus du terminal courant uniquement
ps aux             # tous les processus, syntaxe BSD
ps -ef             # tous les processus, syntaxe System V
```

Les deux dernières sont équivalentes en pratique ; `ps aux` est la plus répandue. Sa sortie :

```
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START  TIME COMMAND
root     1  0.0  0.1 167532 11420 ?     Ss   09:12  0:02 /sbin/init
www-data 812 0.3 1.2 215360 98412 ?     S    09:13  1:45 nginx: worker process
```

| Colonne | Signification |
|---|---|
| `USER` | Utilisateur du processus |
| `PID` | Identifiant |
| `%CPU` | Pourcentage de CPU utilisé (moyenne depuis le démarrage du processus) |
| `%MEM` | Pourcentage de la mémoire physique utilisée |
| `VSZ` | Mémoire virtuelle, en Ko : tout ce que le processus a réservé, même inutilisé. Peu significatif |
| `RSS` | Mémoire **réellement** occupée en RAM, en Ko. C'est la valeur à regarder |
| `TTY` | Terminal associé (`?` pour un service sans terminal) |
| `STAT` | État (voir ci-dessus), avec des suffixes : `s` chef de session, `+` au premier plan, `<` priorité haute, `N` priorité basse |
| `TIME` | Temps CPU total consommé |
| `COMMAND` | Commande complète |

### Personnaliser et trier

```bash
ps -eo pid,ppid,user,%cpu,%mem,rss,cmd                 # colonnes choisies
ps -eo pid,user,%mem,rss,cmd --sort=-%mem | head       # les plus gourmands en mémoire
ps -eo pid,user,%cpu,cmd --sort=-%cpu | head           # les plus gourmands en CPU
ps -p 1234 -o pid,user,etime,cmd                       # un processus précis, avec sa durée de vie
ps -u www-data                                          # processus d'un utilisateur
ps -ef --forest                                         # vue arborescente
```

### Trouver un processus par son nom

```bash
pgrep nginx                # PID des processus dont le nom contient nginx
pgrep -a python            # avec la commande complète
pgrep -u alice             # processus d'alice
pidof sshd                 # PID d'un programme par son nom exact
```

> 💡 Évitez `ps aux | grep python` : la commande `grep python` elle-même apparaît dans les résultats. `pgrep -a python` fait la même chose, proprement.

## 3. Surveiller en temps réel : `top` et `htop`

### `top`

`top` est disponible sur tous les systèmes. Son en-tête résume l'état de la machine :

```
top - 10:32:15 up 3 days,  2:14,  1 user,  load average: 0.52, 0.78, 0.91
Tasks: 142 total,   1 running, 141 sleeping,   0 stopped,   0 zombie
%Cpu(s):  5.2 us,  1.3 sy,  0.0 ni, 92.8 id,  0.5 wa,  0.0 hi,  0.2 si,  0.0 st
MiB Mem :   7851.2 total,   1204.5 free,   2831.9 used,   3814.8 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   4712.3 avail Mem
```

La ligne CPU se lit ainsi :

| Champ | Signification |
|---|---|
| `us` | Temps passé dans le code des programmes (user) |
| `sy` | Temps passé dans le noyau (system) |
| `ni` | Programmes à priorité réduite (nice) |
| `id` | Temps inactif (idle) |
| `wa` | **Attente des entrées/sorties** (I/O wait). Une valeur élevée signale un disque saturé |
| `st` | Temps « volé » par l'hyperviseur, sur une VM (steal). Une valeur élevée signale un hôte surchargé |

Les touches utiles dans `top` :

| Touche | Action |
|---|---|
| `P` | Trier par CPU |
| `M` | Trier par mémoire |
| `1` | Afficher chaque cœur séparément |
| `c` | Afficher la commande complète |
| `u` | Filtrer par utilisateur |
| `k` | Envoyer un signal à un processus |
| `q` | Quitter |

### `htop`

`htop` est une version plus lisible et interactive de `top`, avec des couleurs, la souris, le défilement horizontal et une vue arborescente. Ses raccourcis sont affichés en bas de l'écran : `F3` pour chercher, `F4` pour filtrer, `F5` pour la vue arborescente, `F6` pour trier, `F9` pour envoyer un signal, `F10` pour quitter.

### Comprendre la charge (load average)

Les trois nombres du *load average* représentent la charge moyenne sur la dernière minute, les 5 dernières et les 15 dernières. La charge correspond au nombre moyen de processus qui **veulent** s'exécuter (état `R`) ou qui attendent une entrée/sortie (état `D`).

Ce chiffre ne s'interprète qu'**au regard du nombre de cœurs** :

```bash
nproc              # nombre de cœurs
uptime             # charge actuelle
```

Sur une machine à 4 cœurs, une charge de 4 signifie que les processeurs sont pleinement occupés ; au-delà, des processus font la queue. Une charge de 4 est donc normale sur un serveur à 8 cœurs, mais préoccupante sur un serveur à 2 cœurs.

Les trois valeurs donnent aussi une tendance : `load average: 8.10, 3.20, 1.05` indique un pic récent en train de monter, alors que `1.05, 3.20, 8.10` indique une situation qui revient à la normale.

> 💡 Une charge élevée avec un CPU peu utilisé (`id` élevé) et un `wa` important signale presque toujours un problème de disque, pas de processeur.

## 4. La mémoire

```bash
free -h
```

```
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       2.8Gi       1.2Gi        45Mi       3.7Gi       4.6Gi
Swap:          2.0Gi          0B       2.0Gi
```

La colonne qui compte est **`available`** : c'est la mémoire réellement disponible pour de nouveaux programmes. La colonne `free` est trompeuse, car Linux utilise volontairement la RAM inoccupée comme cache disque (`buff/cache`), qu'il libère instantanément dès qu'un programme en a besoin.

> 💡 « Linux mange toute ma RAM » est une inquiétude fréquente et généralement infondée : une mémoire libre est une mémoire gaspillée. Tant que `available` reste confortable et que le swap n'est pas sollicité, tout va bien.

### Le swap

Le swap est un espace disque utilisé comme mémoire de débordement. Un usage léger et stable est sans conséquence. Un swap qui se remplit activement, en revanche, rend la machine extrêmement lente, car le disque est des milliers de fois plus lent que la RAM.

### L'OOM killer

Quand la mémoire est totalement épuisée, le noyau choisit un processus et le tue pour libérer de la place : c'est l'**OOM killer** (*Out Of Memory*). Il vise en priorité les gros consommateurs. Si une application s'arrête brutalement sans laisser de message dans ses propres logs, pensez-y :

```bash
sudo dmesg -T | grep -i -E "oom|killed process"
sudo journalctl -k | grep -i oom
```

> 💡 Côté Docker, un conteneur qui dépasse sa limite mémoire (`--memory`) est tué de la même façon. `docker inspect` indique alors `"OOMKilled": true`.

## 5. Les signaux

Un **signal** est un message très simple envoyé à un processus par le noyau, par un autre processus ou par l'utilisateur. Chaque signal a un numéro et un nom. Un programme peut choisir de réagir à la plupart des signaux (on dit qu'il les « intercepte »), ou laisser le comportement par défaut s'appliquer.

### Les signaux à connaître

| Signal | N° | Envoyé par | Comportement par défaut | Usage |
|---|---|---|---|---|
| `SIGTERM` | 15 | `kill` sans option | Terminer | **Demande polie** de s'arrêter. Le programme peut finir proprement : fermer ses fichiers, terminer les requêtes en cours |
| `SIGINT` | 2 | `Ctrl+C` | Terminer | Interruption depuis le terminal |
| `SIGKILL` | 9 | `kill -9` | Terminer | **Arrêt immédiat et brutal** par le noyau. Ne peut pas être intercepté ni ignoré |
| `SIGHUP` | 1 | Fermeture du terminal | Terminer | Historiquement « le terminal a raccroché ». De nombreux services l'interprètent comme « **recharge ta configuration** » |
| `SIGTSTP` | 20 | `Ctrl+Z` | Suspendre | Mise en pause depuis le terminal |
| `SIGSTOP` | 19 | `kill -STOP` | Suspendre | Pause forcée, non interceptable |
| `SIGCONT` | 18 | `fg`, `bg`, `kill -CONT` | Reprendre | Reprise d'un processus suspendu |
| `SIGUSR1`, `SIGUSR2` | 10, 12 | Programmes | Terminer | Libres d'usage, définis par chaque application |

```bash
kill -l            # liste de tous les signaux
```

### Envoyer un signal

```bash
kill 1234                  # SIGTERM au processus 1234
kill -TERM 1234            # idem, explicite
kill -HUP 1234             # demander un rechargement
kill -9 1234               # SIGKILL : dernier recours
kill -STOP 1234            # suspendre
kill -CONT 1234            # reprendre

pkill nginx                # SIGTERM à tous les processus dont le nom contient nginx
pkill -u alice             # à tous les processus d'alice
killall python3            # à tous les processus nommés exactement python3
```

> ⚠️ **`kill -9` n'est pas le réflexe par défaut.** Un processus tué par `SIGKILL` n'a aucune chance de faire le ménage : fichiers temporaires laissés en place, écritures à moitié faites, transactions interrompues, fichiers de verrouillage non supprimés qui empêchent le redémarrage. Envoyez toujours d'abord `SIGTERM`, attendez quelques secondes, et n'utilisez `SIGKILL` que si le processus ne répond pas.

> ⚠️ Avec `pkill` et `killall`, vérifiez d'abord la liste des processus concernés avec `pgrep -a` : un motif trop large peut toucher bien plus de processus que prévu.

### Les signaux et les conteneurs

Ce mécanisme explique un comportement qui intrigue beaucoup de développeurs. `docker stop` envoie `SIGTERM` au processus principal du conteneur, attend 10 secondes, puis envoie `SIGKILL`. Si votre conteneur met toujours exactement 10 secondes à s'arrêter, c'est que votre application ne réagit pas à `SIGTERM`.

Deux causes fréquentes. D'abord, le processus principal d'un conteneur est son **PID 1**, et le noyau ne lui applique pas les comportements par défaut des signaux : un PID 1 qui n'intercepte pas explicitement `SIGTERM` l'ignore. Ensuite, la forme « shell » de `CMD` dans un Dockerfile (`CMD python app.py`) lance votre application à travers un `sh`, et c'est `sh` qui reçoit le signal, pas votre application.

Les solutions : utiliser la forme « exec » (`CMD ["python", "app.py"]`), intercepter `SIGTERM` dans l'application pour s'arrêter proprement, et utiliser l'option `--init` de Docker (ou `init: true` dans docker compose), qui place un petit processus init en PID 1 pour relayer les signaux correctement.

## 6. Premier plan, arrière-plan et tâches

### Lancer en arrière-plan

Par défaut, une commande s'exécute **au premier plan** : le shell attend qu'elle se termine avant de rendre la main. Avec `&`, elle s'exécute **en arrière-plan** et le shell est immédiatement disponible :

```bash
sleep 300 &
# [1] 4512                ← numéro de tâche et PID
```

### Gérer les tâches du shell

```bash
jobs               # liste des tâches du shell courant
fg                 # ramène la dernière tâche au premier plan
fg %2              # ramène la tâche numéro 2
bg                 # relance en arrière-plan une tâche suspendue
kill %1            # envoie SIGTERM à la tâche numéro 1
```

Le scénario classique : vous lancez une longue commande au premier plan, puis vous voulez récupérer la main.

```bash
./long-traitement.sh       # la commande occupe le terminal
# Ctrl+Z                   ← suspend la commande
bg                         # la relance en arrière-plan
jobs                       # vérification
```

### Survivre à la fermeture du terminal

Quand un terminal ou une session SSH se ferme, le shell envoie `SIGHUP` à ses tâches, qui s'arrêtent. Pour qu'une commande survive à la déconnexion :

```bash
nohup ./long-traitement.sh > traitement.log 2>&1 &    # ignore SIGHUP dès le lancement
disown %1                                              # détache une tâche déjà lancée
```

### `tmux` : la vraie solution

Sur un serveur, la meilleure approche est un **multiplexeur de terminal** comme `tmux` (ou son ancêtre `screen`). `tmux` crée des sessions qui continuent de tourner sur le serveur même quand vous vous déconnectez, et que vous pouvez retrouver plus tard, exactement dans l'état où vous les avez laissées.

```bash
tmux new -s maintenance    # crée une session nommée
# ... on lance ses commandes ...
# Ctrl+B puis D            ← se détacher de la session
tmux ls                    # lister les sessions
tmux attach -t maintenance # se rattacher
```

Les raccourcis de base (toujours `Ctrl+B`, puis la touche) :

| Raccourci | Action |
|---|---|
| `Ctrl+B` `D` | Se détacher |
| `Ctrl+B` `%` | Couper la fenêtre verticalement |
| `Ctrl+B` `"` | Couper la fenêtre horizontalement |
| `Ctrl+B` flèches | Passer d'un panneau à l'autre |
| `Ctrl+B` `C` | Nouvelle fenêtre |
| `Ctrl+B` `N` / `P` | Fenêtre suivante / précédente |
| `Ctrl+B` `[` | Mode défilement (`q` pour sortir) |

> 💡 Prenez l'habitude de lancer `tmux` **avant** toute opération longue sur un serveur distant (mise à jour, migration de base, copie de gros fichiers). Une coupure réseau au milieu d'une migration lancée sans `tmux` peut coûter très cher.

## 7. Les priorités

Quand plusieurs processus veulent le processeur en même temps, le noyau répartit le temps selon leur **priorité**. Elle se règle avec la valeur *nice*, de **-20** (priorité maximale) à **19** (priorité minimale). Par défaut, elle vaut 0. Plus un processus est « gentil » (*nice*), plus il laisse sa place aux autres.

```bash
nice -n 10 ./sauvegarde.sh         # lancer avec une priorité réduite
renice -n 15 -p 4512               # modifier la priorité d'un processus existant
sudo renice -n -5 -p 4512          # augmenter la priorité : réservé à root
ps -eo pid,ni,cmd --sort=-ni | head
```

Un utilisateur normal peut seulement **réduire** la priorité de ses propres processus. Pour les tâches lourdes et non urgentes (sauvegardes, compressions, indexations), lancer avec `nice` évite de ralentir les services en production.

## 8. Explorer `/proc`

Chaque processus a un dossier `/proc/<PID>/` qui expose ses informations en direct. C'est de là que `ps` et `top` tirent leurs données.

```bash
ls /proc/$$/                       # le dossier de votre shell
cat /proc/$$/status                # état, mémoire, UID, nombre de threads...
tr '\0' ' ' < /proc/$$/cmdline     # la commande complète
tr '\0' '\n' < /proc/$$/environ    # les variables d'environnement
ls -l /proc/$$/cwd                 # dossier courant
ls -l /proc/$$/exe                 # programme exécuté
ls -l /proc/$$/fd/                 # fichiers ouverts
```

Les éléments de `cmdline` et `environ` sont séparés par des caractères nuls, d'où le `tr`.

> 🔒 `/proc/<PID>/environ` montre toutes les variables d'environnement d'un processus, y compris les secrets passés de cette façon (`DATABASE_PASSWORD`...). Il n'est lisible que par le propriétaire du processus et par root, mais c'est une raison de plus de ne pas faire tourner des applications différentes sous le même utilisateur.

## 9. Qui utilise quoi : `lsof`

`lsof` (*list open files*) affiche les fichiers ouverts par les processus. Et comme tout est fichier, cela inclut les connexions réseau.

```bash
lsof -p 1234                       # fichiers ouverts par un processus
sudo lsof /var/log/syslog          # qui a ouvert ce fichier ?
sudo lsof +D /srv/app              # qui utilise des fichiers de ce dossier ?
sudo lsof -i :8080                 # qui écoute ou est connecté sur le port 8080 ?
sudo lsof -i -P -n                 # toutes les connexions réseau
sudo lsof -u www-data              # fichiers ouverts par un utilisateur
```

`fuser` répond plus simplement à la même question :

```bash
sudo fuser -v 8080/tcp             # qui utilise le port 8080
sudo fuser -vm /mnt/disque         # qui empêche de démonter ce disque
```

### Le cas du fichier supprimé mais toujours ouvert

Un grand classique de production : le disque est plein, on supprime un énorme fichier de log, mais **l'espace ne se libère pas**.

Sous Linux, supprimer un fichier retire son nom du dossier, mais ses données restent sur le disque tant qu'un processus le garde ouvert. Le programme qui écrivait dans le log continue d'écrire dans un fichier devenu invisible, et l'espace disque n'est rendu qu'à la fermeture de ce fichier.

```bash
sudo lsof +L1                      # fichiers supprimés mais encore ouverts
```

Deux façons de s'en sortir : redémarrer (ou envoyer `SIGHUP` à) le processus concerné pour qu'il ferme et rouvre ses fichiers, ou vider le fichier sans l'arrêter, via `/proc` :

```bash
: > /proc/<PID>/fd/<N>             # tronque le fichier à 0 octet
```

> 💡 Pour vider un fichier de log en cours d'utilisation, on utilise `: > fichier.log` (ou `truncate -s 0 fichier.log`) plutôt que `rm` : le fichier garde son nom et le processus continue d'y écrire normalement.

## 10. Espionner un programme : `strace`

`strace` affiche en direct les appels système d'un processus, c'est-à-dire tout ce qu'il demande au noyau : fichiers qu'il ouvre, connexions qu'il tente, programmes qu'il lance. C'est un outil de diagnostic redoutable quand un programme échoue avec un message d'erreur inutile.

```bash
strace ls                                  # tous les appels système de ls (très verbeux)
strace -e trace=openat cat /etc/hostname   # uniquement les ouvertures de fichiers
strace -e trace=openat,connect curl -s https://example.com > /dev/null
strace -f -e trace=execve bash -c 'ls | wc -l'   # -f suit les processus enfants
sudo strace -p 1234                        # s'attacher à un processus en cours
strace -c ls                               # statistiques : quels appels, combien de fois
```

Exemple : un programme dit seulement « configuration introuvable ». Quel fichier cherche-t-il ?

```bash
strace -e trace=openat,stat ./monprogramme 2>&1 | grep -i -E "conf|ENOENT"
# openat(AT_FDCWD, "/etc/monprogramme/config.yml", O_RDONLY) = -1 ENOENT (No such file or directory)
```

La réponse apparaît immédiatement, avec le chemin exact et la raison de l'échec (`ENOENT` : fichier inexistant, `EACCES` : permission refusée).

> ⚠️ `strace` ralentit considérablement le programme observé. À utiliser ponctuellement pour un diagnostic, avec prudence sur un processus de production.

### Exercice 5.2 — Charge et priorités (niveau de base)

1. Combien de cœurs votre machine possède-t-elle ? Quelle est la charge actuelle ?
2. Lancez deux processus qui consomment 100 % d'un cœur chacun : `yes > /dev/null &` (deux fois).
3. Observez-les dans `top` (ou `htop`). Quelle part du CPU prend chacun ? Comment évolue la charge ?
4. Réduisez la priorité de l'un des deux au maximum. Qu'observez-vous ? (Pour que l'effet soit visible, lancez autant de `yes` que de cœurs, plus un.)
5. Arrêtez tous les processus `yes` en une commande.

<details>
<summary>Solution</summary>

```bash
nproc
uptime
yes > /dev/null &
yes > /dev/null &
top                         # P pour trier par CPU, 1 pour voir chaque cœur
renice -n 19 -p <PID>
pkill yes
```

Si la machine a plus de cœurs libres que de processus `yes`, chacun obtient un cœur entier et la priorité ne change rien : la priorité n'a d'effet que lorsque des processus sont **en concurrence** pour le même processeur. Avec plus de processus que de cœurs, le processus à nice 19 obtient nettement moins de CPU que les autres.

</details>

### Exercice 5.3 — Les signaux (niveau intermédiaire)

Créez le script `~/signaux.sh` suivant et rendez-le exécutable :

```bash
#!/bin/bash
echo "Je suis le processus $$"
trap 'echo "SIGTERM reçu : je fais le ménage et je quitte proprement"; exit 0' TERM
trap 'echo "SIGINT reçu (Ctrl+C) : je refuse de m arrêter !"' INT
trap 'echo "SIGHUP reçu : je recharge ma configuration"' HUP
while true; do sleep 1; done
```

1. Lancez-le au premier plan et essayez `Ctrl+C`. Que se passe-t-il ?
2. Depuis un second terminal, envoyez-lui successivement `SIGHUP`, `SIGUSR1`, puis relancez-le et envoyez `SIGTERM`. Observez chaque réaction.
3. Relancez-le et envoyez `SIGKILL`. Le message de ménage s'affiche-t-il ? Pourquoi ?
4. Relancez-le, suspendez-le avec `kill -STOP`, vérifiez son état avec `ps`, puis faites-le repartir.

<details>
<summary>Solution</summary>

```bash
chmod +x ~/signaux.sh
~/signaux.sh                # Ctrl+C : le message s'affiche, le script continue
```

Dans un second terminal :

```bash
kill -HUP $(pgrep -f signaux.sh)     # message de rechargement, le script continue
kill -USR1 $(pgrep -f signaux.sh)    # non intercepté : comportement par défaut, le script meurt
kill -TERM $(pgrep -f signaux.sh)    # message de ménage, sortie propre
kill -9 $(pgrep -f signaux.sh)       # aucun message : SIGKILL ne peut pas être intercepté
kill -STOP $(pgrep -f signaux.sh)
ps -o pid,stat,cmd -p $(pgrep -f signaux.sh)    # état T
kill -CONT $(pgrep -f signaux.sh)
```

La réaction peut prendre jusqu'à une seconde : bash n'exécute le `trap` qu'une fois la commande en cours (`sleep 1`) terminée.

</details>

### Exercice 5.6 — Le disque qui ne se libère pas (niveau intermédiaire)

Reproduisez le grand classique de production :

```bash
dd if=/dev/zero of=/tmp/gros.log bs=1M count=500    # un « log » de 500 Mo
df -h /tmp                                          # noter l'espace utilisé
sleep 100000 3< /tmp/gros.log &                     # un processus le garde ouvert
rm /tmp/gros.log
df -h /tmp                                          # l'espace est-il libéré ?
```

1. Pourquoi l'espace disque n'est-il pas revenu ?
2. Retrouvez le fichier fantôme et le processus qui le retient.
3. Récupérez le fichier supprimé (copiez-le ailleurs) grâce à `/proc`.
4. Libérez l'espace **sans arrêter** le processus.

<details>
<summary>Solution</summary>

Le fichier a perdu son nom, mais le processus `sleep` le garde ouvert sur son descripteur 3 : les données restent sur le disque.

```bash
sudo lsof +L1                         # affiche sleep et /tmp/gros.log (deleted)
ls -l /proc/<PID>/fd/                 # 3 -> /tmp/gros.log (deleted)
cp /proc/<PID>/fd/3 /tmp/recupere.log # récupération
: > /proc/<PID>/fd/3                  # troncature : l'espace est rendu
df -h /tmp
kill <PID>
rm /tmp/recupere.log
```


</details>
