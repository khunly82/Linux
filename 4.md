# Chapitre 4 — Utilisateurs, groupes et permissions

## 1. Un système multi-utilisateur

Linux a été conçu dès l'origine pour que plusieurs personnes et plusieurs programmes utilisent la même machine en même temps, sans pouvoir se nuire. Chaque fichier appartient à quelqu'un, chaque processus s'exécute au nom de quelqu'un, et le noyau vérifie les droits à chaque accès.

Ce mécanisme ne sert pas seulement à séparer des humains. Sur un serveur, la plupart des comptes sont des **comptes de service** : `www-data` pour le serveur web, `postgres` pour la base de données, `systemd-network` pour la gestion du réseau... Chaque service tourne avec son propre compte et n'a accès qu'à ce dont il a besoin. Si le serveur web est compromis, l'attaquant obtient les droits de `www-data`, pas ceux de tout le système.

C'est le **principe du moindre privilège**, et c'est probablement la notion de sécurité la plus importante de ce cours.

### root

Le compte **root** (UID 0) est l'administrateur. Le noyau ne lui applique quasiment aucune vérification de permissions : il peut lire, modifier ou supprimer n'importe quel fichier, tuer n'importe quel processus. C'est pour cela qu'on évite de travailler en root au quotidien et qu'on utilise `sudo` ponctuellement.

## 2. Identifiants : UID et GID

Pour le noyau, un utilisateur n'est pas un nom mais un **numéro**, l'UID (User ID). De même, un groupe est identifié par un GID (Group ID). Les noms ne sont qu'une correspondance pratique stockée dans des fichiers texte.

| Plage d'UID (Ubuntu) | Usage |
|---|---|
| 0 | root |
| 1 à 999 | Comptes système et comptes de service |
| 1000 et plus | Comptes humains |

Chaque utilisateur possède un **groupe principal** (généralement un groupe portant son nom) et peut appartenir à plusieurs **groupes secondaires**.

### Qui suis-je ?

```bash
whoami             # nom de l'utilisateur courant
id                 # UID, GID et tous les groupes
id alice           # la même chose pour un autre utilisateur
groups             # liste des groupes
who                # utilisateurs connectés
w                  # utilisateurs connectés et ce qu'ils font
```

```
$ id
uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
```

## 3. Les fichiers de comptes

### `/etc/passwd` : les comptes

Lisible par tous, il contient une ligne par compte, avec 7 champs séparés par `:` :

```
student:x:1000:1000:Student,,,:/home/student:/bin/bash
│       │ │    │    │           │             │
│       │ │    │    │           │             └ shell de connexion
│       │ │    │    │           └ dossier personnel
│       │ │    │    └ description (nom complet...)
│       │ │    └ GID du groupe principal
│       │ └ UID
│       └ mot de passe : « x » signifie qu'il est dans /etc/shadow
└ nom du compte
```

Les comptes de service ont généralement comme shell `/usr/sbin/nologin` ou `/bin/false` : ils existent pour faire tourner des programmes, mais personne ne peut s'y connecter.

### `/etc/shadow` : les mots de passe

Lisible uniquement par root (et le groupe `shadow`), il contient les mots de passe **hachés** et leur politique d'expiration :

```bash
sudo grep student /etc/shadow
# student:$y$j9T$Kd...:20345:0:99999:7:::
```

Le deuxième champ est le hachage du mot de passe. Son préfixe indique l'algorithme (`$y$` pour yescrypt, `$6$` pour SHA-512). S'il commence par `!` ou vaut `*`, le compte ne peut pas se connecter par mot de passe. Les champs suivants concernent l'expiration (date du dernier changement, durée de validité...).

> 💡 Pourquoi deux fichiers ? `/etc/passwd` doit être lisible par tous, car de nombreux programmes ont besoin de convertir un UID en nom (c'est ce que fait `ls -l`). Les hachages de mots de passe ont donc été déplacés dans un fichier protégé pour empêcher les attaques par dictionnaire.

### `/etc/group` : les groupes

```
sudo:x:27:student,alice
│    │ │  │
│    │ │  └ membres secondaires
│    │ └ GID
│    └ mot de passe de groupe (inutilisé)
└ nom du groupe
```

> ⚠️ Ne modifiez jamais ces fichiers à la main avec un éditeur : une erreur de syntaxe peut empêcher toute connexion. Utilisez les commandes prévues, ou à la rigueur `vipw` et `vigr` qui vérifient la syntaxe.

## 4. Gérer les utilisateurs et les groupes

### Créer un utilisateur

Deux commandes existent sous Ubuntu :

```bash
sudo adduser alice                 # interactive, pensée pour les humains
sudo useradd -m -s /bin/bash alice # bas niveau, pensée pour les scripts
```

`adduser` (propre à la famille Debian) crée le home, copie les fichiers de base, choisit un shell et demande un mot de passe. `useradd` est disponible sur toutes les distributions mais ne fait que ce qu'on lui demande : sans `-m` il ne crée pas de home, sans `-s` il attribue souvent `/bin/sh`.

Options utiles de `useradd` :

| Option | Rôle |
|---|---|
| `-m` | Créer le dossier personnel |
| `-s /bin/bash` | Shell de connexion |
| `-G groupe1,groupe2` | Groupes secondaires |
| `-c "Alice Martin"` | Description |
| `-r` | Compte système (UID < 1000, sans home) |
| `-u 1500` | Imposer un UID |

Créer un compte de service pour une application :

```bash
sudo useradd -r -s /usr/sbin/nologin -d /opt/monapp monapp
```

### Mot de passe

```bash
passwd                     # changer son propre mot de passe
sudo passwd alice          # changer celui d'alice
sudo passwd -l alice       # verrouiller le compte
sudo passwd -u alice       # le déverrouiller
sudo chage -l alice        # voir la politique d'expiration
```

### Modifier un utilisateur

```bash
sudo usermod -aG docker alice      # ajouter alice au groupe docker
sudo usermod -s /bin/zsh alice     # changer son shell
sudo usermod -L alice              # verrouiller
```

> ⚠️ **Le piège classique : oublier le `-a`.** `usermod -G docker alice` (sans `-a`) **remplace** tous les groupes secondaires d'alice par le seul groupe `docker`. Si elle faisait partie du groupe `sudo`, elle perd ses droits d'administration. Retenez `-aG` comme un seul mot : *append to Groups*.

### Supprimer un utilisateur

```bash
sudo userdel alice         # supprime le compte, garde ses fichiers
sudo userdel -r alice      # supprime aussi son home
```

### Gérer les groupes

```bash
sudo groupadd devs                 # créer un groupe
sudo gpasswd -a alice devs         # ajouter un membre
sudo gpasswd -d alice devs         # retirer un membre
sudo groupdel devs                 # supprimer le groupe
getent group devs                  # voir les membres
```

> 💡 **Un changement de groupe n'est pris en compte qu'à la prochaine connexion.** Un utilisateur ajouté au groupe `docker` doit se déconnecter et se reconnecter (ou ouvrir un nouveau shell de connexion) pour que `id` affiche le nouveau groupe. C'est la cause de nombreux « j'ai pourtant ajouté le groupe, ça ne marche pas ».

## 5. Changer d'identité : `su` et `sudo`

### `su` : devenir un autre utilisateur

```bash
su - alice         # devenir alice (demande le mot de passe d'alice)
su -               # devenir root (demande le mot de passe de root)
exit               # revenir à l'utilisateur précédent
```

Le tiret est important : `su -` ouvre un vrai shell de connexion avec l'environnement de l'utilisateur cible (son `PATH`, son home...). Sans tiret, on garde une partie de l'environnement précédent, ce qui provoque des comportements surprenants.

### `sudo` : exécuter une commande avec d'autres droits

```bash
sudo apt update            # lance une commande en root
sudo -u postgres psql      # lance une commande en tant que postgres
sudo -i                    # ouvre un shell root
sudo -l                    # affiche ce que j'ai le droit de faire
```

`sudo` demande **votre** mot de passe, pas celui de root. Sur Ubuntu, le compte root n'a d'ailleurs pas de mot de passe par défaut : on passe systématiquement par `sudo`.

Les avantages de `sudo` sur `su` sont importants. On donne des droits d'administration sans partager un mot de passe root commun. On peut limiter les droits à certaines commandes. Et chaque utilisation est journalisée, avec l'utilisateur et la commande exacte :

```bash
sudo grep sudo /var/log/auth.log | tail
# ... student : TTY=pts/0 ; PWD=/home/student ; USER=root ; COMMAND=/usr/bin/apt update
```

### Configurer `sudo`

Les règles se trouvent dans `/etc/sudoers` et, plus proprement, dans des fichiers séparés sous `/etc/sudoers.d/`. On les édite **toujours** avec `visudo`, qui vérifie la syntaxe avant d'enregistrer :

```bash
sudo visudo                        # éditer /etc/sudoers
sudo visudo -f /etc/sudoers.d/bob  # éditer un fichier dédié
```

> ⚠️ Une erreur de syntaxe dans les fichiers sudoers peut bloquer `sudo` pour tout le monde, et donc vous empêcher de réparer. `visudo` vous en protège : ne modifiez jamais ces fichiers autrement.

Syntaxe d'une règle :

```
qui   sur_quelle_machine=(en_tant_que_qui)   quelles_commandes
```

Exemples :

```
# Tous les droits pour alice
alice   ALL=(ALL:ALL) ALL

# Tous les droits pour les membres du groupe sudo (règle par défaut sur Ubuntu)
%sudo   ALL=(ALL:ALL) ALL

# bob peut redémarrer nginx, et seulement ça, sans mot de passe
bob     ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx

# Le groupe deploy peut lancer le script de déploiement en tant que l'utilisateur app
%deploy ALL=(app) NOPASSWD: /opt/app/deploy.sh
```

Le `%` désigne un groupe. Les commandes doivent être indiquées avec leur **chemin complet** (`which systemctl` pour le trouver).

> 🔒 Méfiez-vous des règles trop larges. Autoriser `sudo vim`, `sudo less` ou `sudo find` revient à donner un accès root complet, car ces programmes permettent de lancer un shell. Même chose pour un script modifiable par l'utilisateur lui-même.

## 6. Les permissions

### Propriétaire, groupe, autres

Chaque fichier a un **propriétaire** (un utilisateur) et un **groupe**. Les permissions sont définies pour trois catégories :

- **u** (*user*) : le propriétaire ;
- **g** (*group*) : les membres du groupe du fichier ;
- **o** (*others*) : tous les autres.

Et pour chacune, trois droits : **r** (lecture), **w** (écriture), **x** (exécution).

```
-rwxr-x--- 1 alice devs 1234 Sep 15 10:00 deploy.sh
 └┬┘└┬┘└┬┘   └─┬─┘ └┬─┘
  │  │  │      │    └ groupe du fichier
  │  │  │      └ propriétaire
  │  │  └ autres : aucun droit
  │  └ groupe devs : lecture et exécution
  └ alice : lecture, écriture, exécution
```

Le noyau vérifie les catégories **dans l'ordre** et s'arrête à la première qui correspond : si vous êtes le propriétaire, seuls les droits du propriétaire s'appliquent, même si ceux du groupe sont plus larges.

### Sur un fichier et sur un dossier, ce n'est pas pareil

| Droit | Sur un fichier | Sur un dossier |
|---|---|---|
| `r` | Lire le contenu | Lister les noms des fichiers (`ls`) |
| `w` | Modifier le contenu | **Créer, renommer, supprimer** des fichiers dedans |
| `x` | Exécuter comme programme | **Traverser** le dossier : y entrer (`cd`) et accéder à ses fichiers |

Deux conséquences surprennent souvent.

Supprimer un fichier ne dépend pas des droits sur le fichier, mais des droits d'**écriture sur le dossier** qui le contient. On peut donc supprimer un fichier en lecture seule dont on n'est pas propriétaire, si on a le droit `w` sur son dossier.

Pour accéder à `/srv/app/config/app.yml`, il faut le droit `x` sur **chaque dossier du chemin** : `/`, `/srv`, `/srv/app` et `/srv/app/config`. Un seul maillon manquant et c'est « Permission denied », même si le fichier lui-même est lisible par tous.

### `chmod` en notation symbolique

```bash
chmod u+x script.sh        # ajoute l'exécution au propriétaire
chmod g-w fichier          # retire l'écriture au groupe
chmod o= fichier           # retire tous les droits aux autres
chmod a+r fichier          # ajoute la lecture à tous (all)
chmod ug=rw,o=r fichier    # définit précisément
chmod +x script.sh         # exécution pour tous
```

### `chmod` en notation octale

Chaque droit a une valeur : **r = 4**, **w = 2**, **x = 1**. On additionne pour chaque catégorie :

| Chiffre | Droits | | Chiffre | Droits |
|---|---|---|---|---|
| 7 | `rwx` | | 3 | `-wx` |
| 6 | `rw-` | | 2 | `-w-` |
| 5 | `r-x` | | 1 | `--x` |
| 4 | `r--` | | 0 | `---` |

Les valeurs à connaître :

| Octal | Symbolique | Usage typique |
|---|---|---|
| `644` | `rw-r--r--` | Fichier ordinaire |
| `755` | `rwxr-xr-x` | Dossier, script ou programme |
| `600` | `rw-------` | Fichier privé : clé SSH, fichier `.env` avec des secrets |
| `700` | `rwx------` | Dossier privé : `~/.ssh` |
| `640` | `rw-r-----` | Configuration lisible par un groupe de service |
| `750` | `rwxr-x---` | Dossier d'application réservé à un groupe |

```bash
chmod 600 ~/.ssh/id_ed25519
chmod 755 ~/bin/monscript.sh
```

### Récursivité

```bash
chmod -R g+w dossier/              # applique à tout le contenu
chmod -R u=rwX,g=rX,o= dossier/    # X majuscule : x seulement sur les dossiers
```

Le `X` majuscule est précieux : il ajoute le droit d'exécution aux dossiers (pour pouvoir les traverser) sans rendre tous les fichiers exécutables. `chmod -R 755` sur un dossier de code rend au contraire chaque fichier exécutable, ce qui n'a pas de sens.

> ⚠️ **`chmod 777` n'est jamais la solution.** Cela donne à n'importe quel utilisateur et à n'importe quel processus de la machine le droit de modifier ou remplacer le fichier. Si vous êtes tenté de l'utiliser pour « débloquer » quelque chose, c'est qu'il faut comprendre qui a besoin de quel accès, et corriger le propriétaire ou le groupe.

### `chown` et `chgrp` : changer de propriétaire

```bash
sudo chown alice fichier           # change le propriétaire
sudo chown alice:devs fichier      # change propriétaire et groupe
sudo chown :devs fichier           # change seulement le groupe
sudo chgrp devs fichier            # idem
sudo chown -R www-data:www-data /var/www/monsite
```

Seul root peut changer le propriétaire d'un fichier. Un utilisateur peut changer le groupe de ses propres fichiers, mais seulement vers un groupe dont il fait partie.

### `umask` : les droits par défaut

Quand un fichier est créé, il ne reçoit pas tous les droits : le `umask` indique ceux qu'il faut **retirer**.

```bash
umask              # 0022 sur la plupart des systèmes
```

Les fichiers sont créés au maximum en `666` et les dossiers en `777`. Avec un umask de `022`, on retire l'écriture au groupe et aux autres : les fichiers sont donc créés en `644` et les dossiers en `755`. Un umask de `027` (plus strict) donne `640` et `750`.

## 7. Les droits spéciaux

Trois droits supplémentaires existent, avec une valeur octale placée **devant** les trois chiffres habituels.

### setuid (4) : exécuter avec les droits du propriétaire

Un programme avec le bit setuid s'exécute avec les droits de son **propriétaire**, et non de l'utilisateur qui le lance.

```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root 64152 ... /usr/bin/passwd
```

Le `s` à la place du `x` du propriétaire indique le setuid. C'est ce qui permet à un simple utilisateur de changer son mot de passe : `passwd` doit écrire dans `/etc/shadow`, que seul root peut modifier.

> 🔒 Un programme setuid root mal écrit est une faille directe vers root. C'est l'une des premières choses que vérifie un attaquant, et donc un administrateur : `find / -perm -4000 -type f 2>/dev/null`.

### setgid (2) sur un dossier : hériter du groupe

Sur un dossier, le bit setgid fait que tout fichier créé dedans **appartient au groupe du dossier**, et non au groupe principal de son créateur. C'est indispensable pour un dossier partagé entre plusieurs personnes.

```bash
sudo chmod g+s /srv/projet         # ou : chmod 2775 /srv/projet
ls -ld /srv/projet
# drwxrwsr-x 2 root devs 4096 ... /srv/projet
```

### sticky bit (1) : chacun ses fichiers

Sur un dossier, le sticky bit empêche un utilisateur de supprimer ou renommer les fichiers des autres, même s'il a le droit d'écriture sur le dossier. C'est le cas de `/tmp`, où tout le monde peut écrire :

```bash
ls -ld /tmp
# drwxrwxrwt 18 root root 4096 ... /tmp
```

Le `t` final indique le sticky bit.

| Octal | Signification | Exemple |
|---|---|---|
| `4755` | setuid + `rwxr-xr-x` | `/usr/bin/passwd` |
| `2770` | setgid + `rwxrwx---` | Dossier partagé d'une équipe |
| `1777` | sticky + `rwxrwxrwx` | `/tmp` |
| `3770` | setgid + sticky + `rwxrwx---` | Dossier d'équipe où chacun ne peut supprimer que ses fichiers |

## 8. Les ACL : des permissions plus fines

Le modèle propriétaire/groupe/autres atteint vite ses limites : comment donner un accès en lecture seule à **une** personne supplémentaire, sans créer un nouveau groupe ? Les ACL (Access Control Lists) permettent d'ajouter des règles pour des utilisateurs ou groupes précis.

```bash
sudo apt install acl
setfacl -m u:charlie:rx /srv/projet        # charlie peut lire et traverser
setfacl -m g:auditeurs:r rapport.pdf       # le groupe auditeurs peut lire
getfacl /srv/projet                        # afficher les ACL
setfacl -x u:charlie /srv/projet           # retirer la règle de charlie
setfacl -b /srv/projet                     # retirer toutes les ACL
```

Les **ACL par défaut** s'appliquent automatiquement aux nouveaux fichiers créés dans un dossier :

```bash
setfacl -d -m u:charlie:rx /srv/projet
```

Un `+` à la fin des permissions dans `ls -l` signale la présence d'ACL :

```
drwxrws---+ 2 root devs 4096 ... /srv/projet
```

## 9. Permissions et processus

Un processus s'exécute avec l'identité de l'utilisateur qui l'a lancé, et c'est cette identité qui est vérifiée à chaque accès à un fichier. Pour savoir pourquoi une application n'arrive pas à lire sa configuration, il faut donc d'abord savoir **sous quel utilisateur elle tourne** :

```bash
ps -eo user,pid,cmd | grep nginx
# root      1234 nginx: master process
# www-data  1235 nginx: worker process
```

### Permissions et Docker

Ce point concerne directement les développeurs. Par défaut, les processus d'un conteneur tournent en **root**. Et comme le noyau ne raisonne qu'en numéros, l'UID 0 du conteneur est aussi l'UID 0 de la machine hôte. Conséquence : les fichiers créés par un conteneur dans un volume monté appartiennent à root sur votre machine.

```bash
mkdir ~/test-docker && cd ~/test-docker
docker run --rm -v "$PWD":/data ubuntu touch /data/cree-par-docker
ls -l
# -rw-r--r-- 1 root root 0 ... cree-par-docker     ← appartient à root : impossible à modifier sans sudo
```

Deux solutions : lancer le conteneur avec votre UID et votre GID, ou déclarer un utilisateur non privilégié dans le Dockerfile.

```bash
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD":/data ubuntu touch /data/fichier-ok
```

```dockerfile
RUN useradd -r -u 1001 app
USER app
```

> 🔒 Faire tourner une application en root dans un conteneur est une mauvaise pratique pour les mêmes raisons que sur un serveur : en cas de faille, l'attaquant hérite des droits root, et une évasion du conteneur devient beaucoup plus grave.

> ⚠️ Même remarque pour le groupe `docker` : un utilisateur qui en fait partie peut lancer `docker run -v /:/host ...` et obtenir un accès root à toute la machine. Être dans le groupe `docker` équivaut à être root.

## 10. Diagnostiquer un « Permission denied »

Face à une erreur de permission, procédez méthodiquement plutôt que de lancer des `chmod` au hasard.

1. **Qui essaie d'accéder ?** `id` pour vous, `ps -eo user,cmd` pour un service.
2. **À quoi ?** Le chemin complet du fichier.
3. **Quels sont les droits sur tout le chemin ?** C'est là que `namei` est irremplaçable :

```bash
namei -l /srv/app/config/app.yml
# f: /srv/app/config/app.yml
# drwxr-xr-x root root  /
# drwxr-xr-x root root  srv
# drwxr-x--- app  app   app          ← les autres ne peuvent pas traverser
# drwxr-xr-x app  app   config
# -rw-r--r-- app  app   app.yml
```

4. **Tester en tant que l'utilisateur concerné :**

```bash
sudo -u www-data cat /srv/app/config/app.yml
```

5. **Corriger au plus juste** : ajouter l'utilisateur au bon groupe, changer le groupe du dossier, ajouter une ACL. Pas de `777`.

### Les permissions qu'exige SSH

SSH refuse d'utiliser des clés dont les permissions sont trop ouvertes. C'est une source d'erreurs fréquente, que nous retrouverons au chapitre 10 :

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519 ~/.ssh/authorized_keys
chmod 644 ~/.ssh/id_ed25519.pub
```

## 11. Exercices

Sauf indication contraire, les exercices se font dans un conteneur du lab, où l'on peut créer et casser des comptes sans risque :

```bash
cd ~/lab
docker compose exec web bash       # shell root dans le conteneur web
```

Depuis ce shell root, `su - alice` permet de devenir alice sans mot de passe, ce qui facilite les tests.

### Exercice 4.1 — Qui suis-je ? (niveau de base)

Dans votre Ubuntu WSL :

1. Affichez votre UID, votre GID et vos groupes.
2. Trouvez votre ligne dans `/etc/passwd` et identifiez chaque champ.
3. Combien de comptes ont un UID supérieur ou égal à 1000 ?
4. Quel est le shell du compte `www-data` ? Que signifie-t-il ?
5. Qui fait partie du groupe `sudo` ?

<details>
<summary>Solution</summary>

```bash
id
grep "^$(whoami):" /etc/passwd
awk -F: '$3 >= 1000' /etc/passwd | wc -l     # attention, « nobody » a l'UID 65534
grep "^www-data:" /etc/passwd | cut -d: -f7  # /usr/sbin/nologin : connexion impossible
getent group sudo
```

</details>

### Exercice 4.2 — Créer des comptes (niveau de base)

Dans le conteneur `web` :

1. Créez les utilisateurs `alice`, `bob` et `charlie`, avec un dossier personnel et bash comme shell.
2. Donnez-leur à chacun un mot de passe.
3. Créez un groupe `devs` et ajoutez-y alice et bob.
4. Vérifiez avec `id` pour chacun.
5. Devenez alice et vérifiez que vous êtes bien dans votre home.

<details>
<summary>Solution</summary>

```bash
for u in alice bob charlie; do useradd -m -s /bin/bash "$u"; done
echo -e "alice:alice\nbob:bob\ncharlie:charlie" | chpasswd   # ou : passwd alice
groupadd devs
usermod -aG devs alice
usermod -aG devs bob
id alice; id bob; id charlie
su - alice
pwd
exit
```

</details>

### Exercice 4.3 — Lire et écrire des permissions (niveau de base)

1. Convertissez en octal : `rw-r-----`, `rwxr-xr-x`, `rw-------`, `rwxrws---`.
2. Convertissez en symbolique : `640`, `711`, `1777`, `4755`.
3. Créez un fichier `secret.txt` lisible et modifiable uniquement par vous, de deux façons différentes.
4. Créez un script `hello.sh` qui affiche « Bonjour », et rendez-le exécutable pour vous seulement. Lancez-le.

<details>
<summary>Solution</summary>

1. `640`, `755`, `600`, `2770`
2. `rw-r-----`, `rwx--x--x`, `rwxrwxrwt`, `rwsr-xr-x`

```bash
touch secret.txt
chmod 600 secret.txt

echo 'echo Bonjour' > hello.sh
chmod u+x hello.sh

```

### Exercice 4.4 — Le dossier partagé de l'équipe (niveau intermédiaire)

Mettez en place un dossier `/srv/projet` pour l'équipe `devs` qui respecte ces règles :

- alice et bob peuvent y créer des fichiers, et peuvent modifier les fichiers l'un de l'autre ;
- tous les fichiers créés dedans appartiennent automatiquement au groupe `devs` ;
- charlie ne peut ni lire ni lister le dossier.

Testez chaque règle en devenant successivement alice, bob et charlie.

<details>
<summary>Solution</summary>

```bash
mkdir /srv/projet
chown root:devs /srv/projet
chmod 2770 /srv/projet
ls -ld /srv/projet             # drwxrws--- root devs

su - alice -c 'echo "note alice" > /srv/projet/note.txt; ls -l /srv/projet'
su - bob -c 'echo "ajout bob" >> /srv/projet/note.txt'   # échoue !
```

Le fichier appartient bien au groupe `devs` grâce au setgid, mais il a été créé en `644` à cause du umask `022` : le groupe n'a pas le droit d'écriture. Deux corrections possibles :

```bash
# Corriger le fichier existant
chmod g+w /srv/projet/note.txt

# Et pour les suivants : un umask 002 pour les membres de l'équipe
echo "umask 002" >> /home/alice/.profile
echo "umask 002" >> /home/bob/.profile
```

Une ACL par défaut est une alternative plus robuste, qui ne dépend pas du umask de chaque utilisateur (voir l'exercice 4.7).

```bash
su - bob -c 'echo "ajout bob" >> /srv/projet/note.txt'   # fonctionne
su - charlie -c 'ls /srv/projet'                         # Permission denied
```

</details>

### Exercice 4.5 — Chacun ses fichiers (niveau intermédiaire)

Dans le dossier de l'exercice précédent, bob peut actuellement supprimer les fichiers d'alice. Vérifiez-le, puis modifiez le dossier pour que chacun puisse modifier les fichiers des autres mais ne puisse supprimer que les siens.

<details>
<summary>Solution</summary>

```bash
su - alice -c 'touch /srv/projet/a-alice.txt'
su - bob -c 'rm /srv/projet/a-alice.txt'        # fonctionne : w sur le dossier

chmod +t /srv/projet                            # ou : chmod 3770 /srv/projet
ls -ld /srv/projet                              # drwxrws--T

su - alice -c 'touch /srv/projet/a-alice.txt'
su - bob -c 'rm /srv/projet/a-alice.txt'        # Operation not permitted
```

Le `T` majuscule indique un sticky bit sans droit d'exécution pour les autres, ce qui est normal ici.

</details>

### Exercice 4.8 — Diagnostic : « Permission denied » (niveau intermédiaire)

En root dans le conteneur, préparez la situation suivante :

```bash
useradd -r -s /usr/sbin/nologin app
mkdir -p /srv/app/config
echo "db_password: s3cr3t" > /srv/app/config/app.yml
chown -R root:root /srv/app
chmod 750 /srv/app
chmod 755 /srv/app/config
chmod 644 /srv/app/config/app.yml
```

L'application, qui tourne sous l'utilisateur `app`, n'arrive pas à lire sa configuration :

```bash
sudo -u app cat /srv/app/config/app.yml
```

Trouvez la cause avec `namei`, puis corrigez le problème **proprement** : l'utilisateur `app` doit pouvoir lire sa configuration, mais les autres utilisateurs ne doivent pas pouvoir lire le mot de passe qu'elle contient.

<details>
<summary>Solution</summary>

```bash
namei -l /srv/app/config/app.yml
# drwxr-x--- root root app     ← app n'est ni propriétaire, ni dans le groupe root : pas de x
```

Correction : donner le dossier au groupe `app`, et protéger le fichier de configuration qui contient un secret.

```bash
chgrp -R app /srv/app
chmod 640 /srv/app/config/app.yml
namei -l /srv/app/config/app.yml

sudo -u app cat /srv/app/config/app.yml         # fonctionne
su - charlie -c 'cat /srv/app/config/app.yml'   # Permission denied
```

La configuration initiale avait un second problème, moins visible : le fichier était en `644`, donc lisible par tous dès que le dossier devenait traversable. Corriger uniquement le dossier en `755` aurait « réparé » l'application tout en exposant le mot de passe.

</details>
